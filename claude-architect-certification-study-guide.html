Part 01The Agentic Loop

What Is the Agentic Loop?

The agentic loop is the fundamental execution pattern behind all Claude-based agents. It is an iterative cycle in which the model reasons about a task, decides whether to call a tool, executes that tool, feeds the result back into the conversation, and then reasons again — repeating until the task is complete.

Agentic Loop Flow

User request → LLM reasoning → tool call → execute tool → tool result → LLM reasoning → response (or more tool calls)

Key Components

  • System prompt — Defines the agent's role, capabilities, and behavioral constraints
  • Conversation history — The full message array (user + assistant + tool_result turns)
  • Tool definitions — JSON schemas describing available functions the model may call
  • Thinking — Extended thinking blocks where the model reasons through complex decisions

The stop_reason Field

Every API response includes a stop_reason that tells the orchestrator what to do next:

stop_reasonMeaningOrchestrator Action
end_turnModel finished naturallyExit the loop — task is complete
tool_useModel wants to call a toolExecute the tool, feed result back, continue loop
max_tokensHit the output token limitResponse was truncated — handle or extend
refusalModel declined on safety groundsEscalate, rephrase, or use a fallback model
stop_sequenceHit a custom stop stringHandle per application logic

Loop Termination Conditions

A well-designed agentic loop must have explicit termination conditions beyond just end_turn:

  • Task complete — stop_reason == "end_turn"
  • Max iterations reached — Prevent infinite loops (e.g., cap at 20 iterations)
  • Error threshold — Stop after N consecutive tool errors
  • Context window limit — Approaching the token ceiling, must summarize or stop
  • Cost ceiling — Accumulated token spend exceeds a budget

Python Agentic Loop Example

Pythonimport anthropic client = anthropic.Anthropic() tools = [...] # tool definitions messages = [{"role": "user", "content": task}] while True: response = client.messages.create( model="claude-opus-5-5", max_tokens=4096, tools=tools, messages=messages ) # Task complete — exit the loop if response.stop_reason == "end_turn": final_text = next( (b.text for b in response.content if b.type == "text"), "" ) print(final_text) break # Extract tool calls and execute them for block in response.content: if block.type == "tool_use": result = execute_tool(block.name, block.input) messages.append({ "role": "assistant", "content": response.content }) messages.append({ "role": "user", "content": [{ "type": "tool_result", "tool_use_id": block.id, "content": result }] })

Token Accumulation

Every iteration of the agentic loop adds tokens to the context window. The assistant's response, the tool result, and any reasoning all consume tokens. In a long-running agent:

  • Input tokens grow with every iteration (the full conversation is re-sent)
  • Tool results can be large (file contents, search results, API responses)
  • Without management, the context window fills and the agent fails
Exam Tip The agentic loop continues until stop_reason == "end_turn". When stop_reason == "tool_use", the orchestrator must execute the tool, append the result, and call the API again. Always set max iteration limits to prevent infinite loops.

Part 02Hub-and-Spoke Model

Architecture Pattern

The hub-and-spoke model is an orchestration pattern where one central orchestrator agent (the hub) decomposes complex tasks and delegates subtasks to specialized worker agents (the spokes). The hub collects results, synthesizes them, and maintains overall task coherence.

Hub Responsibilities
  • Task decomposition — Break a complex request into discrete subtasks
  • Delegation — Route each subtask to the appropriate specialist agent
  • Result aggregation — Collect and merge outputs from all spokes
  • Quality control — Validate spoke outputs, request retries if needed

Spoke Agent Characteristics

  • Narrowly scoped — Each spoke handles one type of task (e.g., code review, testing, documentation)
  • Single-purpose — Focused system prompt and limited tool set
  • Isolated context — Each spoke has its own context window, independent of the hub and other spokes
  • Stateless between invocations — Spokes receive only the data they need for their subtask

Comparison of Orchestration Patterns

PatternFlowBest ForComplexity
Sequential (Chain)A → B → C (pipeline)Deterministic multi-step workflowsLow
RouterClassify → Route to specialistInput classification + specialized handlingLow-Medium
Fan-Out / Fan-InHub sends to N spokes simultaneously, collects all resultsParallelizable work (translations, multi-file edits)Medium
Hub-and-SpokeHub decomposes, delegates dynamically, aggregatesComplex tasks requiring multiple skillsHigh

Hub-and-Spoke vs. Monolithic Agent

DimensionMonolithic AgentHub-and-Spoke
ScalabilityLimited by single context windowEach spoke has its own context
DebuggingHard to isolate failuresEach spoke can be tested independently
SpecializationOne prompt for everythingTailored prompts per task type
Model selectionOne model for all tasksDifferent models per spoke (Haiku for triage, Opus for reasoning)
ComplexitySimple to implementRequires orchestration logic

Claude Code's Sub-Agent Pattern

Claude Code implements hub-and-spoke natively. The main agent (hub) can spawn background sub-agents (spokes) using the Agent tool. Each sub-agent runs with its own context and tool set, optionally in an isolated git worktree to avoid file conflicts.

Exam Tip Hub-and-spoke is ideal when a task requires multiple skills, can be decomposed, and benefits from different models or prompts for different subtasks. The hub never does the detailed work itself — it orchestrates.

Part 03Task Tool and Parallel Execution

Task Tool: Spawning Sub-Agents

The task tool (or Agent tool in Claude Code) is the mechanism for spawning sub-agents to handle discrete tasks. Each sub-agent operates independently with its own conversation history, system prompt, and tool set.

Parallel Tool Use

Claude can call multiple tools in a single response. When the model determines that several operations are independent, it emits multiple tool_use blocks in one turn. The orchestrator should execute them concurrently for maximum throughput.

Python# A response may contain multiple tool calls tool_calls = [b for b in response.content if b.type == "tool_use"] # Execute all tool calls in parallel import asyncio async def run_parallel(calls): tasks = [execute_tool_async(c.name, c.input) for c in calls] return await asyncio.gather(*tasks) results = asyncio.run(run_parallel(tool_calls)) # Send all results back as a single user message tool_results = [ {"type": "tool_result", "tool_use_id": c.id, "content": r} for c, r in zip(tool_calls, results) ] messages.append({"role": "user", "content": tool_results})

Controlling Parallel Execution

ParameterValueEffect
disable_parallel_tool_usetrueLimit Claude to one tool call per turn — useful for sequential dependencies
disable_parallel_tool_usefalse (default)Allow multiple tool calls per response

Worktree Isolation

When multiple agents work on the same codebase simultaneously, file conflicts are a real risk. Claude Code solves this with worktree isolation: each sub-agent operates in its own git worktree (a separate checkout of the same repository), avoiding conflicts entirely.

  • Each worktree has its own working directory and branch
  • Agents can commit independently without stepping on each other
  • After completion, changes are merged back to the main branch

Task Decomposition Strategies

By File

Each agent handles a different file or set of files. Best for multi-file refactoring.

By Function

Each agent implements a different function or feature. Best for greenfield development.

By Concern

Separate agents for code, tests, docs, config. Best for full-stack changes.

By Test

Each agent fixes one failing test. Best for large test suites with many failures.

Exam Tip Use disable_parallel_tool_use: true when tool calls have sequential dependencies. Leave it as default (false) when tools are independent to maximize throughput. Worktree isolation prevents file conflicts between parallel agents.

Part 04Programmatic Control and Hooks

Hooks: Shell Commands on Claude Code Actions

Hooks are shell commands that execute automatically before or after Claude Code performs specific actions. They provide programmatic control over the agent's behavior without modifying the model itself.

Hook Types

Hook TypeWhen It FiresUse Case
PreToolUseBefore a tool runsValidate inputs, block dangerous operations, log actions
PostToolUseAfter a tool completesAuto-format code, run linters, trigger tests
NotificationWhen a notification firesSend alerts to Slack, log events
StopWhen the agent stopsCleanup, final validation, summary generation

Hook Configuration

JSON{ "hooks": { "PreToolUse": [{ "matcher": "Write", "command": "echo 'About to write file: $CLAUDE_FILE_PATH'" }], "PostToolUse": [{ "matcher": "Write", "command": "npx prettier --write $CLAUDE_FILE_PATH" }, { "matcher": "Bash", "command": "npm test 2>&1 | tail -5" }] } }

Hook Environment Variables

  • $CLAUDE_FILE_PATH — The file being written or edited
  • $CLAUDE_TOOL_NAME — The name of the tool being used
  • Hook commands have access to the full shell environment

Common Hook Use Cases

Auto-Format

PostToolUse on Write: run Prettier, Black, or gofmt after every file edit.

Lint Gate

PostToolUse on Write: run ESLint or pylint and feed errors back to Claude.

Test Runner

PostToolUse on Bash: automatically run tests after code changes.

Schema Validation

PreToolUse: validate JSON schemas before allowing writes to config files.

Part 05Tool Descriptions

Why Tool Descriptions Are Critical

Tool descriptions are the single most important factor determining whether Claude uses a tool correctly. The model reads tool descriptions as part of its system prompt to decide when to call a tool, how to format inputs, and what to expect from outputs. Poor descriptions lead to misuse, wasted tokens, and errors.

Anatomy of a Good Tool Description

A Description Should Answer
  • What it does — Clear statement of the tool's purpose
  • When to use it — Scenarios that warrant calling this tool
  • What it returns — Format and structure of the output
  • Edge cases — What happens when input is invalid or data is not found
  • Limitations — Rate limits, data freshness, scope restrictions

Good vs. Bad Descriptions

BAD: Vague and Incomplete
"Gets weather"

Claude does not know what input format to use, what the return looks like, or when to choose this tool over alternatives.

GOOD: Specific and Complete
"Get current weather conditions for a city. Input: city name (string). Returns: JSON with temperature_celsius (number), humidity_percent (number), and conditions (string: 'sunny', 'cloudy', 'rainy', 'snowy'). Use when the user asks about current weather in a specific location. Returns an error if the city name is not recognized."

Parameter Descriptions

Every parameter in the input_schema should have its own "description" field:

JSON{ "name": "search_documents", "description": "Search the knowledge base for relevant documents...", "input_schema": { "type": "object", "properties": { "query": { "type": "string", "description": "Natural language search query. Be specific." }, "max_results": { "type": "integer", "description": "Maximum documents to return (1-20). Default: 5." } }, "required": ["query"] } }

Tool Naming Conventions

Use clear verb_noun patterns: get_weather, search_documents, create_user, delete_file. Avoid ambiguous names like process, handle, or do_thing.

Token Cost of Tool Descriptions

Tool definitions are injected into the system prompt and count toward input tokens on every API call. Over-describing tools wastes tokens; under-describing causes misuse. Aim for the minimum description that prevents ambiguity.

Exam Tip Tool descriptions determine Claude's tool selection behavior. They should specify what, when, return format, and edge cases. Tool definitions count toward input tokens on every request — keep them concise but complete.

Part 06Error Handling Patterns

Tool Error Signaling

When a tool execution fails, the orchestrator should signal the error to Claude using the is_error: true flag in the tool_result. This tells Claude that the tool failed and it should try an alternative approach or report the failure.

JSON{ "type": "tool_result", "tool_use_id": "toolu_01ABC...", "content": "Error: Database connection timeout after 5000ms. The database server at db.example.com:5432 is not responding.", "is_error": true }

Error Categories

CategoryExamplesStrategy
Transient429 rate limit, 500 server error, 529 overloaded, network timeoutRetry with exponential backoff
Permanent400 bad request, 404 not found, invalid schemaFail immediately, do not retry
User-fixableMissing credentials, invalid input, permission deniedAsk the user for correction

Retry with Exponential Backoff

Pythonimport time, anthropic def call_with_backoff(client, max_retries=3, **kwargs): for attempt in range(max_retries): try: return client.messages.create(**kwargs) except anthropic.RateLimitError: wait = 2 ** attempt # 1s, 2s, 4s time.sleep(wait) except anthropic.APIStatusError as e: if e.status_code >= 500: time.sleep(2 ** attempt) else: raise # 4xx = permanent, do not retry raise Exception("Max retries exceeded")

SDK Auto-Retry

The official Python and TypeScript SDKs automatically retry 429 (rate limit) and 529 (overloaded) errors with exponential backoff. You do not need to implement retry logic for these specific cases when using the SDK.

Circuit Breaker Pattern

If a tool fails repeatedly, stop calling it entirely to avoid wasting tokens and time:

  • Closed (normal) — tool calls proceed as usual
  • Open (tripped) — after N consecutive failures, skip the tool and use a fallback
  • Half-open — after a timeout, try one call to see if the service recovered

Graceful Degradation

When a tool fails, Claude should fall back to a simpler approach rather than stopping entirely. For example, if a web search tool fails, Claude can reason from its training data. If a database tool fails, Claude can suggest the user run the query manually.

HTTP Error Codes Reference

CodeMeaningAction
400Bad RequestFix the request payload
401UnauthorizedCheck API key
429Rate LimitedAuto-retry (SDK handles this)
500Server ErrorRetry with backoff
529OverloadedAuto-retry (SDK handles this)
Exam Tip Always use is_error: true when returning a tool error to Claude — without it, Claude may interpret the error text as a successful result. The SDK auto-retries 429 and 529 errors; you must handle 500s yourself.

Part 07MCP Configuration

What Is MCP?

MCP (Model Context Protocol) is an open standard for connecting AI models to external tools and data sources. Instead of building custom tool integrations for each service, MCP provides a standardized protocol that any server can implement and any client can consume.

MCP Connector in Messages API

The Messages API supports connecting to remote MCP servers directly, without needing a separate MCP client:

JSON{ "model": "claude-sonnet-5", "max_tokens": 1024, "mcp_servers": [{ "type": "url", "url": "https://mcp.example.com/sse", "name": "my-server", "authorization": { "type": "bearer", "token": "sk-..." }, "tool_configuration": { "allowed_tools": ["search", "create"], "denied_tools": ["delete"] } }], "messages": [...] }

MCP in Claude Code

Claude Code supports MCP server configuration in two locations:

  • .claude/settings.json — project-level MCP servers (committed to repo)
  • .mcp.json — alternative project-level configuration file
  • ~/.claude/settings.json — user-level MCP servers (personal tools)

Key MCP Features

Tool Discovery

MCP servers expose available tools dynamically. The client discovers what tools are available at connection time.

Multiple Servers

Connect to multiple MCP servers in a single request. Each server contributes its own set of tools.

OAuth Support

MCP supports OAuth authentication for servers that require user-specific authorization.

Per-Tool Configuration

Use allowed_tools and denied_tools to control which tools from a server Claude can access.

MCP vs. Custom Tools

DimensionMCPCustom Tools
ProtocolStandardized, openBespoke per application
DiscoveryDynamic (server advertises tools)Static (defined at build time)
InteroperabilityAny MCP client can use any MCP serverTightly coupled to your app
HostingServer runs independentlyYou implement the tool execution
Best forShared services, third-party integrationsApp-specific business logic
Exam Tip MCP is an open standard, not proprietary. It enables dynamic tool discovery and works across any compliant client/server. Use tool_configuration to allowlist or denylist specific tools from an MCP server.

Part 08Tool Scoping and Agent Roles

Principle of Least Privilege

Each agent should have access to only the tools it needs for its specific role. Broader tool access increases the risk of errors, security vulnerabilities, and wasted tokens (more tool definitions = more input tokens).

Role-Based Tool Access Patterns

Agent RoleTools AvailableRationale
Researcherweb_search, web_fetch, read_fileRead-only access to gather information
Coderwrite_file, edit_file, bash, test_runnerFull write access to implement changes
Reviewerread_file, grep, diffRead-only — can analyze but not modify
Deployerbash (limited commands), gitRestricted to deployment operations

Tool Choice Modes

ModeBehaviorUse Case
autoClaude decides whether to use toolsDefault for most agentic loops
anyClaude must use at least one toolForce tool use when you know a tool is needed
toolClaude must use a specific named toolForce a specific tool call (e.g., structured output)
noneClaude cannot use any toolsText-only response, no tool calling

Benefits of Scoping

  • Fewer errors — agents cannot accidentally use the wrong tool
  • Better security — read-only agents cannot modify files or run commands
  • Lower token cost — fewer tool definitions means fewer input tokens per call
  • Clearer reasoning — agents make better tool selections from a smaller set

Agent Isolation

Beyond tool scoping, each agent should have:

  • Separate system prompts — tailored to its specific role
  • Isolated context — its own conversation history, not shared with other agents
  • Scoped permissions — limited file system and network access
Exam Tip Tool scoping reduces errors, cost, and security risk. A reviewer agent should never have write tools. Use tool_choice: "none" to force text-only responses and tool_choice: {type: "tool", name: "..."} to force a specific tool call.

Part 09CLAUDE.md Hierarchy

What Is CLAUDE.md?

CLAUDE.md is a project instruction file that Claude Code reads at session start. It provides the model with persistent context about your project: coding standards, architecture decisions, build commands, testing conventions, and more.

The Hierarchy (General to Specific)

LevelLocationScopeExample Content
1. User~/.claude/CLAUDE.mdAll projects for this userPersonal preferences, editor settings, default model
2. Project Root/project/CLAUDE.mdEntire projectArchitecture, coding standards, build commands
3. Directory/project/src/CLAUDE.mdSource directory and belowModule-specific patterns, import conventions
4. Subdirectory/project/src/api/CLAUDE.mdAPI directory and belowAPI conventions, endpoint patterns, auth handling

Override Behavior

More specific CLAUDE.md files override more general ones. If the root CLAUDE.md says "use tabs" but src/api/CLAUDE.md says "use 2-space indent", the API directory uses 2-space indent. The hierarchy merges additively for non-conflicting rules.

What to Put in CLAUDE.md

DO Include
  • Non-obvious architecture decisions
  • Coding standards specific to this project
  • Build and deployment commands
  • Testing conventions and patterns
  • Preferred libraries and frameworks
  • Review checklists
DO NOT Include
  • Things derivable from code itself
  • Standard language conventions
  • Information already in git history
  • API keys or secrets
  • Redundant information from package.json

AGENTS.md

AGENTS.md is an alternative name that is also read by Claude Code. Both filenames work identically. Use whichever naming convention your team prefers.

Auto Memory

Claude Code automatically saves learnings across sessions in ~/.claude/memory. This is separate from CLAUDE.md and stores things Claude discovers during work (e.g., "this project uses pnpm, not npm").

Exam Tip The CLAUDE.md hierarchy goes from user (~/.claude/CLAUDE.md) to project root to subdirectories. More specific files override more general ones. Keep it concise and focus on non-obvious decisions.

Part 10Agent Skills

What Are Skills?

Skills are packaged, repeatable workflows that can be invoked by name. They provide a way to create standardized procedures that any team member can trigger, ensuring consistent execution of common tasks.

Invoking Skills

  • /skill-name — Slash command in Claude Code CLI
  • Skill tool — Programmatic invocation from within an agent
  • Skills load their instructions on demand (progressive disclosure)

Skill Types

TypeExamplesDescription
Built-in/code-review, /init, /security-reviewIncluded with Claude Code, always available
Custom/deploy-staging, /run-tests, /generate-docsCreated in .claude/skills/ directory

Skills vs. CLAUDE.md

DimensionCLAUDE.mdSkills
NaturePassive context — always loadedActive workflow — invoked on demand
Token costAlways in context (uses tokens every turn)Loaded only when invoked (progressive disclosure)
Use caseStandards, conventions, architectureRepeatable procedures, workflows, checklists
SharingCommitted to repoCommitted to repo (.claude/skills/)

Custom Skill Anatomy

A custom skill is defined by a file in .claude/skills/ with a name, description, and instructions. Skills can include scripts that execute as part of the workflow.

Exam Tip Skills use progressive disclosure — their instructions are loaded on demand, keeping the base context small. CLAUDE.md is always in context; skills are loaded only when invoked.

Part 11Path-Specific Rules and Context Fork

Path-Specific Rules

Different directories in a project can have different CLAUDE.md files, providing path-specific rules. When Claude Code works in a subdirectory, it picks up that directory's CLAUDE.md in addition to the project root's.

Example: Monorepo with Different Standards
  • /CLAUDE.md — Global: "Use conventional commits, run CI before merging"
  • /backend/CLAUDE.md — "Java 17, Spring Boot, JUnit 5, 4-space indent"
  • /frontend/CLAUDE.md — "React 18, TypeScript strict mode, 2-space indent, Vitest"
  • /infrastructure/CLAUDE.md — "Terraform, HCL format, plan before apply"

Context Forking

When an agent enters a subdirectory (or a sub-agent is spawned to work in one), it picks up the directory-specific CLAUDE.md rules. This creates a context fork — the sub-agent operates under different rules than the parent.

Worktree Isolation for Parallel Work

The EnterWorktree tool creates an isolated git worktree for an agent to work in. This provides:

  • File isolation — no conflicts with other agents or the main checkout
  • Independent commits — each worktree has its own branch
  • Clean lifecycle — create → work → commit → merge → cleanup

Fork Pattern

The fork pattern combines context forking with worktree isolation:

  1. Hub agent decomposes a task into subtasks
  2. For each subtask, spawn a sub-agent in its own worktree
  3. Each sub-agent picks up path-specific CLAUDE.md rules
  4. Each sub-agent has its own context window
  5. Results are merged back to the main branch
Exam Tip Path-specific CLAUDE.md files let different parts of a monorepo have different coding standards. Worktree isolation prevents file conflicts between parallel agents. Context fork = different agent, different rules, different context window.

Part 13Match Criteria and Few-Shot Examples

Match Criteria for Hooks and Skills

Hooks and skills use match criteria to determine when they should trigger. The matcher defines which tool or action activates the hook.

Matcher TypeSyntaxExample
ExactTool name string"Write" — matches the Write tool
GlobWildcard pattern"Bash(*)" — matches any Bash invocation
RegexRegular expression/^(Write|Edit)$/ — matches Write or Edit

Few-Shot Examples in Prompts

Few-shot examples demonstrate the expected behavior to Claude. They are one of the most effective techniques for improving output quality and consistency.

Best Practices for Examples

  • 3-5 examples for best results — fewer may be insufficient, more wastes tokens
  • Diverse — cover different scenarios, edge cases, and input types
  • Relevant — examples should match the distribution of real inputs
  • Structured — use consistent formatting so the pattern is clear

Example Structure

XML Tags<examples> <example> <input>What is the refund policy for digital products?</input> <output> Category: billing Confidence: 0.95 Response: Digital products are eligible for a full refund within 14 days of purchase if unused... </output> </example> <example> <input>My account is locked after too many login attempts</input> <output> Category: technical Confidence: 0.98 Response: Account lockouts are automatically cleared after 30 minutes. If you need immediate access... </output> </example> </examples>

Tool Use Examples

You can also provide examples showing Claude how to use tools correctly. Include them as sample conversations in the system prompt to demonstrate the expected tool selection and parameter formatting.

Exam Tip Use 3-5 diverse, structured examples wrapped in <example> tags. Match criteria for hooks support exact names, glob patterns, and regex. Examples demonstrate expected behavior; match criteria define trigger conditions.

Part 14JSON Schema and Structured Output

Guaranteed Schema Conformance

The Messages API supports output_config.format with a JSON Schema, guaranteeing that the model's output conforms to the specified schema. This eliminates parsing errors and post-processing validation.

Python: Pydantic Integration

Pythonfrom pydantic import BaseModel import anthropic class SentimentResult(BaseModel): sentiment: str # "positive", "negative", "neutral" confidence: float reasoning: str client = anthropic.Anthropic() result = client.messages.parse( model="claude-sonnet-5", max_tokens=1024, messages=[{"role": "user", "content": "Analyze: 'This product is amazing!'"}], output_schema=SentimentResult ) # result is a SentimentResult instance with type safety print(result.sentiment) # "positive"

TypeScript: Zod Integration

TypeScriptimport Anthropic from "@anthropic-ai/sdk"; import { z } from "zod"; import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod"; const SentimentSchema = z.object({ sentiment: z.enum(["positive", "negative", "neutral"]), confidence: z.number(), reasoning: z.string() }); const result = await client.messages.create({ model: "claude-sonnet-5", max_tokens: 1024, messages: [{ role: "user", content: "Analyze: 'Terrible experience'" }], output_config: zodOutputFormat(SentimentSchema) });

Strict Tool Definitions

Setting strict: true on a tool definition ensures that Claude's tool call parameters exactly match the JSON Schema, with no extra fields:

JSON{ "name": "create_ticket", "description": "Create a support ticket", "strict": true, "input_schema": { "type": "object", "properties": { ... }, "required": [...], "additionalProperties": false } }

Supported JSON Schema Features

Supported

object, array, string, number, boolean, null, enum, const, anyOf, allOf, $ref/$defs

Limitations

  • No recursive schemas
  • No min/max constraints (minLength, maxLength, minimum, maximum)
  • additionalProperties: false is required on all objects
  • First request with a new schema has higher latency (grammar compilation); compiled grammars are cached for 24 hours
Exam Tip Use client.messages.parse() in Python (with Pydantic) or zodOutputFormat() in TypeScript (with Zod) for type-safe structured output. The first request with a new schema is slower due to grammar compilation. additionalProperties: false is required.

Context Window Sizes

What Counts Toward the Context Window

  • System prompt — including all tool definitions
  • Messages — full conversation history (user + assistant turns)
  • Tool definitions — JSON schemas for all available tools
  • Tool results — returned data from executed tools (often the largest contributor)
  • Images — base64-encoded images or references
  • Thinking blocks — extended thinking content
  • Output — the model's response counts against the window

Context Rot

Context rot is the degradation of model accuracy as the context window fills. Even though the model can technically handle 1M tokens, performance on specific instructions and recall of early context degrades as more content is added. The model may:

  • Forget instructions from the system prompt
  • Miss relevant information buried in long conversations
  • Produce lower-quality outputs due to attention dilution

Compaction

Claude Code supports server-side auto-summarization (compaction) when the conversation approaches the context limit. The system automatically summarizes older parts of the conversation to free up space while preserving the most important information.

Management Strategies

Summarize History

Periodically replace old conversation turns with a summary. Keep recent turns verbatim, summarize older ones.

Drop Old Tool Results

Replace large tool results from earlier turns with a brief summary of what was found.

Use Compaction

Rely on server-side compaction for long-running sessions. The system handles summarization automatically.

Memory Tool

For multi-session work, use the memory tool to persist important context across sessions rather than keeping it in the window.

Overflow Behavior

  • Input too large — 400 error before processing even begins
  • Output exceeds window — stop_reason: "model_context_window_exceeded"

Token Counting API

Use the token counting API to estimate token usage before sending a request. This helps avoid context window errors and manage costs proactively.

Exam Tip Context rot degrades quality as the window fills — curate what is in context. Prompt caching changes cost but not size (cached content still occupies the window). Compaction is automatic server-side summarization. Haiku has only 200K context vs. 1M for the other models.

Part 17Escalation Triggers

When to Escalate

Not every situation should be handled automatically by an agent. Escalation triggers define when the system should stop and involve a human or fall back to a different approach.

Escalation Patterns

PatternTriggerAction
Confidence-BasedAgent reports uncertainty or low confidenceRoute to human for review/decision
Error-BasedN consecutive tool failuresAlert human, stop automated processing
Policy-BasedCertain operations (delete, deploy, financial)Always require human approval
Cost-BasedEstimated cost exceeds budget thresholdPause and confirm before continuing

Refusal Handling

When Claude returns stop_reason: "refusal", the model has declined to respond on safety grounds. Architect-level handling involves:

  • Server-side fallback — Use the fallbacks parameter for automatic model fallback
  • Fallback credit — Anthropic avoids double prompt-cache cost on retries
  • Rephrase and retry — Modify the prompt to avoid triggering the safety filter
  • Escalate to human — Flag for human review when automated resolution fails

Human-in-the-Loop

The human-in-the-loop pattern keeps a human in the approval chain for critical operations:

  1. Agent drafts the action (code change, deployment, email)
  2. System presents the draft to a human reviewer
  3. Human approves, modifies, or rejects
  4. If approved, the agent executes the action

Interruption in Managed Agents

In Managed Agents, you can send additional user_event messages to a running session to steer the agent mid-execution. This enables real-time course correction without stopping the entire task.

Monitoring for Escalation

  • Refusal rate — Track how often the model declines requests
  • Error rate — Track tool failure frequency and patterns
  • Cost anomalies — Alert on sudden spikes in token usage or API costs
  • Latency outliers — Flag unusually slow responses
Exam Tip Know the four escalation patterns: confidence-based, error-based, policy-based, and cost-based. The fallbacks parameter enables automatic model fallback when the primary model refuses. Managed Agents support mid-execution interruption via additional user events.

Correct: D. Haiku 4.5 has a 200K token context window, while Fable 5.1, Opus 5.5, and Sonnet 5 all have 1M token context windows. This is an important consideration when choosing models for tasks requiring large context.
Q46 Escalation Triggers

Which escalation pattern pauses the agent when estimated cost exceeds a budget threshold?

  • A Confidence-based escalation
  • B Error-based escalation
  • C Policy-based escalation
  • D Cost-based escalation
Correct: D. Cost-based escalation pauses the agent and requests human confirmation when the estimated or accumulated cost exceeds a defined budget threshold. This prevents runaway spending in agentic loops.
Q47 Escalation Triggers

What does the fallbacks parameter enable in the Messages API?

  • A Automatic retry of the same model with different parameters
  • B Automatic fallback to alternative models when the primary model refuses or errors
  • C A backup system prompt used when the primary one is too long
  • D Automatic model upgrade when the requested model is unavailable
Correct: B. The fallbacks parameter specifies alternative models to try when the primary model refuses (stop_reason: "refusal") or encounters an error. It includes fallback credit to avoid double prompt-cache costs.
Q48 Escalation Triggers

In Managed Agents, how can you steer an agent mid-execution?

  • A By modifying the system prompt in a separate API call
  • B By killing and restarting the session with new instructions
  • C By sending additional user events to the running session
  • D Mid-execution steering is not supported; you must wait for completion
Correct: C. Managed Agents support interruption by sending additional user_event messages to a running session. This allows real-time course correction without stopping the agent entirely.
Q49 Error Context / Common Mistakes

What is the MOST common mistake that causes infinite loops in agentic systems?

  • A Using too many tools in the tool definitions
  • B Not setting a maximum iteration limit on the agentic loop
  • C Using Haiku instead of Opus for the agentic loop
  • D Setting temperature too high
Correct: B. Without a max iteration limit, the agentic loop can run indefinitely if the model keeps requesting tool calls without reaching end_turn. This causes runaway costs and resource consumption. Always set a cap (e.g., 20 iterations).
Q50 Error Context / Common Mistakes

When returning tool errors to Claude, what information should be included for optimal error recovery?

  • A Only the error code with no additional context
  • B The full stack trace for debugging purposes
  • C What was attempted, what failed, and relevant state (e.g., server address, retry count)
  • D A generic "An error occurred" message to keep responses simple
Correct: C. Error context should include three things: what was attempted ("Tried to query table 'users'"), what failed ("Connection timeout after 5000ms"), and relevant state ("Server: db.example.com:5432, retry 2/3"). This enables Claude to diagnose issues and try alternative approaches.
