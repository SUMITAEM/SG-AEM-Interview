Part 01 — Domain 1: Agentic Architecture and OrchestrationThe Agentic Loop

Introduction to Domain 1: Agentic Architecture and Orchestration

Domain 1 of the CCAR-F exam covers the foundational patterns that power AI agents: the agentic loop, orchestration models (hub-and-spoke), parallel execution, and programmatic control hooks. Understanding these patterns is essential for designing production-grade AI systems that are reliable, cost-effective, and safe.

What Is Claude?

Claude is a family of large language models (LLMs) built by Anthropic. The model family includes multiple tiers optimized for different use cases:

  • Fable 5.1 — Highest capability, designed for multi-day agentic tasks and demanding reasoning
  • Opus 5.5 — Complex reasoning and nuanced analysis
  • Sonnet 5 — General-purpose balanced model (best cost/quality ratio)
  • Haiku 4.5 — Fastest and cheapest, ideal for classification and routing

Claude's core capabilities include natural language understanding, code generation, tool use (function calling), vision (image analysis), extended thinking (chain-of-thought reasoning), and structured output generation. Claude is accessed via the Messages API and can be orchestrated into agentic workflows through tool calling.

What Is the Agentic Loop?

The agentic loop is the fundamental execution pattern behind all Claude-based agents. It is an iterative cycle in which the model reasons about a task, decides whether to call a tool, executes that tool, feeds the result back into the conversation, and then reasons again — repeating until the task is complete.

Agentic Loop Flow Diagram

User Request → LLM Reasoning → tool_use (stop_reason) → Execute Tool → tool_result (append to history) → LLM Reasoning → Response (or more tool calls)

The loop is driven by the stop_reason field in each API response. When the model returns stop_reason: "tool_use", the orchestrator must execute the requested tool, append the result, and call the API again. When it returns stop_reason: "end_turn", the task is finished.

Understanding the stop_reason Field

Every API response includes a stop_reason that tells the orchestrator what to do next. This is the single most important field for controlling the agentic loop:

stop_reasonMeaningOrchestrator Action
end_turnModel finished naturallyExit the loop — task is complete
tool_useModel wants to call one or more toolsExecute the tool(s), feed result(s) back, continue loop
max_tokensHit the output token limitResponse was truncated — continue or increase max_tokens
refusalModel declined on safety groundsEscalate, rephrase, or use fallback model
stop_sequenceHit a custom stop stringHandle per application logic
model_context_window_exceededOutput grew beyond available contextSummarize history and retry, or break task into smaller pieces

How to Branch on tool_use

When the API response comes back, your orchestrator code must check whether stop_reason == "tool_use", then extract each tool call block and dispatch it to the correct handler:

Python# Check stop_reason and branch on tool_use if response.stop_reason == "tool_use": # Extract all tool_use blocks from the response tool_blocks = [b for b in response.content if b.type == "tool_use"] for block in tool_blocks: # Switch on tool name to route to the correct handler if block.name == "search_documents": result = search_documents(block.input) elif block.name == "read_file": result = read_file(block.input["path"]) elif block.name == "write_file": result = write_file(block.input["path"], block.input["content"]) else: result = f"Unknown tool: {block.name}"

How to Append Tool Results to History

After executing a tool, you must append two messages to the conversation history in the correct order. This is one of the most error-prone parts of building an agentic loop:

Python# Step 1: Append the ASSISTANT message with the full response.content # (this includes the tool_use block that Claude generated) messages.append({ "role": "assistant", "content": response.content # MUST include the tool_use block }) # Step 2: Append a USER message with the tool_result # CRITICAL: tool_use_id must match the id from the tool_use block messages.append({ "role": "user", "content": [{ "type": "tool_result", "tool_use_id": block.id, # MUST match the tool_use block id "content": result }] })
Critical: The tool_use_id Must Match Every tool_result block must include the tool_use_id field set to the exact id from the corresponding tool_use block in the assistant's response. If these do not match, the API will reject the request. When multiple tools are called in one turn, each result must be paired with its correct ID.

How to Continue the Loop Correctly

The full agentic loop uses a while loop with a break on end_turn and a max-iterations safety cap:

Pythonimport anthropic client = anthropic.Anthropic() tools = [...] # tool definitions messages = [{"role": "user", "content": task}] MAX_ITERATIONS = 20 # Safety cap to prevent infinite loops for i in range(MAX_ITERATIONS): response = client.messages.create( model="claude-sonnet-5", max_tokens=4096, tools=tools, messages=messages ) # Task complete — exit the loop if response.stop_reason == "end_turn": final_text = next( (b.text for b in response.content if b.type == "text"), "" ) print(final_text) break # Append assistant turn, then execute tools and append results messages.append({"role": "assistant", "content": response.content}) tool_results = [] for block in response.content: if block.type == "tool_use": result = execute_tool(block.name, block.input) tool_results.append({ "type": "tool_result", "tool_use_id": block.id, "content": result }) messages.append({"role": "user", "content": tool_results}) else: print("WARNING: Max iterations reached!")

Common Mistake: Skipping History on Tool Results

If you do not append the assistant turn (the message containing the tool_use block) before appending the tool_result, Claude loses the context of what it asked for. This leads to:

  • Repeated calls — Claude re-requests the same tool because it does not know the result was already obtained
  • Hallucinated results — Claude invents tool output instead of using the real result
  • API errors — The API may reject the request because the tool_result references a tool_use_id that does not appear in the preceding assistant message
WRONG: Missing Assistant Turn
# BUG: appending tool_result WITHOUT the assistant turn first messages.append({ "role": "user", "content": [{"type": "tool_result", "tool_use_id": block.id, "content": result}] }) # Claude won't know what tool_use_id refers to!

Common Mistake: Ending the Loop Too Early

Another common bug is breaking the loop on the first text block, even when more tool calls follow. A single response can contain both text blocks and tool_use blocks. You must check all content blocks for tool_use, not just stop at the first text block:

  • Wrong: if any(b.type == "text" for b in response.content): break
  • Right: Check stop_reason, not individual block types. Only break when stop_reason == "end_turn"
Exam Tip The agentic loop continues until stop_reason == "end_turn". When stop_reason == "tool_use", the orchestrator must: (1) append the full assistant response to history, (2) execute the tool, (3) append a user message with tool_result and matching tool_use_id, (4) call the API again. Always set max iteration limits.

Part 02Hub-and-Spoke Model

Introduction to the Hub-and-Spoke Model

The hub-and-spoke model is an orchestration pattern where one central coordinator agent (the hub) decomposes complex tasks and delegates subtasks to specialized worker agents (the spokes). Communication is one-way delegation: the hub sends tasks to spokes and collects results. Spokes never communicate directly with each other.

How Communication Flows in Hub-and-Spoke

Communication Flow
  1. Hub sends task → A spoke receives a focused subtask with necessary context
  2. Spoke executes → The spoke works independently within its own context window
  3. Spoke returns result → The spoke sends its output back to the hub
  4. Hub aggregates → The hub collects all spoke results and synthesizes a final response

Key rule: Spokes never talk to each other. All coordination flows through the hub.

How a Coordinator Decomposes Tasks

The hub breaks complex tasks into discrete subtasks that can be handled independently. Effective decomposition requires:

  • Identify independent units — Split by file, function, concern, or domain
  • Minimize dependencies — Each subtask should be completable without the output of other subtasks
  • Right-size the work — Each subtask should fit within a single agent's context window
  • Include acceptance criteria — Each spoke should know what "done" looks like

How a Coordinator Invokes Subagents

The invocation mechanism differs by platform:

PlatformMechanismExample
Claude CodeAgent toolSpawn a background sub-agent with a prompt and optional worktree isolation
Messages APISeparate messages.create callsEach spoke is a fresh API call with its own system prompt and tools
Managed AgentsSessionsServer-hosted agents with managed sandboxes and persistent sessions

How to Pass Context to a Subagent

Each spoke should receive only the context it needs — not the hub's full conversation. Keep spoke context small and focused:

  • Include: The specific subtask, relevant code/data, constraints, expected output format
  • Exclude: The hub's full conversation history, other spokes' tasks, irrelevant context
  • Why: Smaller context means fewer tokens, faster processing, and better focus

How a Coordinator Aggregates Results

After all spokes return, the hub must synthesize their outputs into a coherent final response:

  • Collect all outputs — Wait for all spokes to complete (or timeout)
  • Resolve conflicts — If two spokes produce conflicting results, the hub decides which to use
  • Merge appropriately — Concatenate independent outputs, integrate overlapping ones
  • Validate completeness — Verify that all subtasks were addressed

How a Coordinator Handles Subagent Errors

  • Retry failed spokes — For transient failures, re-invoke the spoke with the same task
  • Skip non-critical failures — If a spoke's output is optional, proceed without it
  • Report errors in output — Include failure information in the aggregated result so the user knows what did not complete
  • Escalate critical failures — If a required spoke fails repeatedly, escalate to a human

Why Subagents Have No Memory of the Coordinator

Each spoke is a fresh API call or agent. There is no shared state, no knowledge of the hub's full conversation, and no memory across invocations. This is by design:

  • Spokes are stateless — they receive input and produce output without side effects
  • The hub must include all necessary context in the sub-prompt
  • This isolation makes spokes independently testable and replaceable

How to Diagnose Incomplete Coordinator Output

When the hub's final output is missing information, check these common causes:

  • Did all spokes return? — A spoke may have timed out or errored silently
  • Did the hub wait for all spokes? — The hub may have proceeded before all results arrived
  • Is the context window full? — The hub's context may be too full to include all spoke results
  • Did the hub summarize instead of including all results? — The hub may have condensed outputs, losing detail

Retrieval-Augmented Generation (RAG) with Claude

RAG is a pattern that enhances Claude's responses by injecting relevant documents as context before generation. It is not training — it is context injection at query time:

RAG Pipeline Flow
  1. Embed documents — Convert knowledge-base documents into vector embeddings
  2. Vector search — When a user asks a question, find the most relevant document chunks by cosine similarity
  3. Inject context — Include the retrieved chunks in the system prompt or user message
  4. Claude answers — Claude generates a response grounded in the retrieved context, with citations

Key RAG considerations:

  • Chunking strategy — Split documents into meaningful chunks (by section, paragraph, or fixed token count)
  • Similarity threshold — Set a minimum cosine similarity to avoid injecting irrelevant content
  • Token budget — Retrieved context consumes input tokens — balance relevance vs. cost
  • Citation — Ask Claude to cite which retrieved chunks informed its answer
Exam Tip In hub-and-spoke, spokes never communicate with each other — all coordination flows through the hub. Each spoke is a fresh call with no memory of the hub's conversation. RAG is context injection (not training): embed → search → inject → generate.

Part 03Task Tool and Parallel Execution

Introduction to the Task Tool

The task tool (called the Agent tool in Claude Code) is the mechanism for spawning discrete sub-tasks. Each sub-task runs independently with its own conversation history, system prompt, and tool set. The task tool enables the hub-and-spoke pattern by providing a concrete way for coordinators to delegate work.

Why Coordinators Need task in allowedTools

If the coordinator agent does not have the task/Agent tool in its allowedTools list, it cannot delegate. Instead, it will try to do everything itself within a single context window. This leads to:

  • Context window overflow on large tasks
  • Lower quality output (one prompt trying to do everything)
  • No parallelism — all work is sequential within one agent
  • No specialization — one set of tools for all subtask types
Common Gotcha If your coordinator is trying to do all the work itself instead of delegating, check that Agent (or task) is in its allowedTools list. Without it, the coordinator has no mechanism to spawn sub-agents.

How to Run Subagents in Parallel

In Claude Code, you run subagents in parallel by including multiple Agent tool calls in a single response. Each agent runs in its own context with optional worktree isolation (fan-out pattern):

Python# Claude Code: multiple Agent tool calls in one response = parallel execution # Each agent gets its own worktree to avoid file conflicts # API-level parallel execution: import asyncio async def run_parallel_agents(subtasks): # Create separate API calls for each subtask tasks = [] for subtask in subtasks: task = client.messages.create( model="claude-sonnet-5", system=subtask["system_prompt"], tools=subtask["tools"], messages=[{"role": "user", "content": subtask["task"]}] ) tasks.append(task) return await asyncio.gather(*tasks)

When to Use Sequential vs. Parallel Invocation

Use Sequential WhenUse Parallel When
Task B depends on Task A's outputTasks are fully independent of each other
Order of execution mattersNo shared state between tasks
Each step validates the previous oneTasks can be independently verified
Example: parse input → validate → transformExample: translate to 5 languages simultaneously

Dependency analysis first: Before deciding on parallel vs. sequential, map out dependencies between subtasks. If Task B needs Task A's output, they must be sequential. If they share no data, parallelize them.

What Is the Stakes-Proportionate Rule?

The stakes-proportionate rule is a design principle for agentic systems: match the level of verification and review depth to the risk level of the operation.

Stakes LevelParallelismVerificationExamples
Low stakesAggressive parallelism OKMinimal review, auto-mergeFormatting, docs, adding comments
Medium stakesModerate parallelismAutomated tests, diff reviewCode changes, config updates
High stakesSequential, slowerHuman review, multi-step validationDatabase migrations, deployments, financial

For high-stakes changes, use more verification steps and lower parallelism. For low-stakes changes, parallelize aggressively and reduce review overhead.

Exam Tip The coordinator must have Agent/task in its allowedTools to delegate. Use parallel execution for independent tasks and sequential for dependent ones. The stakes-proportionate rule: high-risk = more verification, less parallelism; low-risk = aggressive parallelism, less review.

Part 04Programmatic Control and Hooks

What Is a Programmatic Gate?

A programmatic gate is a code-level check that blocks or modifies a tool call before execution. Unlike a prompt instruction (which is probabilistic), a gate is deterministic — it always runs and always enforces its rules. Programmatic gates are implemented as hooks or middleware in the agent's orchestration layer.

Prompt vs. Gate

Prompt (probabilistic): "Never write to files outside the /src directory" — Claude might still do it occasionally.

Gate (deterministic): A PreToolUse hook that checks the file path and blocks writes outside /src — always enforced, no exceptions.

Introduction to Tool Call Interception Hooks (PreToolUse)

PreToolUse hooks run before a tool executes. They can inspect the tool call, validate inputs, block dangerous operations, or modify parameters:

  • Validation — Check that file paths are within allowed directories
  • Policy enforcement — Block writes to production config files
  • Logging — Record every tool call for audit trails
  • Transformation — Modify tool inputs before execution (e.g., sanitize paths)

Introduction to PostToolUse Hooks

PostToolUse hooks run after a tool completes. They operate on the output or trigger follow-up actions:

  • Formatting — Run Prettier, Black, or gofmt after every file write
  • Testing — Automatically run tests after code changes
  • Logging — Record tool outputs for debugging
  • Cleanup — Remove temporary files created during execution

Why Prompts Alone Cannot Guarantee Correctness

Prompts are probabilistic — Claude might ignore or misinterpret instructions. Hooks are deterministic — code always runs. For production systems, use both:

AspectPromptsHooks (Programmatic Gates)
EnforcementProbabilistic — Claude may not followDeterministic — code always executes
ReliabilityWorks most of the time, not all100% reliable when correctly coded
Best forGuidance, preferences, styleSecurity, compliance, critical rules
ImplementationSystem prompt textShell commands or scripts

Use both: Prompts for guidance (so Claude tries to follow the rules), hooks for enforcement (so violations are blocked even when Claude does not comply).

Hook Configuration JSON Example with Matchers

JSON{ "hooks": { "PreToolUse": [ { "matcher": "Write", "command": "python validate_path.py $CLAUDE_FILE_PATH" }, { "matcher": "Bash", "command": "python check_command_safety.py" } ], "PostToolUse": [ { "matcher": "Write", "command": "npx prettier --write $CLAUDE_FILE_PATH" }, { "matcher": "Bash", "command": "npm test 2>&1 | tail -5" } ], "Stop": [ { "command": "echo 'Session ended' >> /tmp/claude-audit.log" } ] } }

Hooks are configured in settings.json (in the .claude/ directory), not in CLAUDE.md. The matcher field specifies which tool triggers the hook (exact name, glob, or regex). Hook commands have access to environment variables like $CLAUDE_FILE_PATH and $CLAUDE_TOOL_NAME.

Exam Tip Prompts are probabilistic; hooks are deterministic. Use prompts for guidance, hooks for enforcement. PreToolUse hooks block/validate before execution; PostToolUse hooks format/test after execution. Hooks are configured in settings.json, not CLAUDE.md.

Part 05 — Domain 2: Tool Design and MCP IntegrationTool Descriptions

Introduction to Domain 2: Tool Design and MCP Integration

Domain 2 covers how to design tools that Claude can use effectively, including descriptions, naming, parameter schemas, MCP integration, error handling, and scoping tools to agent roles. Well-designed tools are the foundation of reliable agentic systems.

Why Tool Descriptions Drive Selection

Tool descriptions are the single most important factor determining whether Claude uses a tool correctly. The model reads descriptions as part of its system prompt to decide when to call a tool, how to format inputs, and what to expect from outputs. Poor descriptions lead to misuse, wasted tokens, and errors.

What Vague Descriptions Look Like

BAD: Vague and Incomplete
"Gets data"

Claude does not know what data, what format, when to use it vs. alternatives, or what inputs to provide.

GOOD: Specific and Complete
"Retrieves user profile by user_id from the PostgreSQL users table. Returns JSON with name (string), email (string), and created_at (ISO 8601 date). Use when you need user details for personalization. Returns 404 error if user_id does not exist. Use find_users instead when searching by name or email with partial matches."

How to Diagnose Tool Misselection

If Claude is choosing the wrong tool, check these factors:

  • Is the description ambiguous? — Could it be confused with another tool?
  • Does it overlap with another tool? — Two tools with similar descriptions compete
  • Is the parameter schema clear? — Unclear parameters lead to wrong inputs
  • Does the tool name clearly indicate its purpose? — process_data is ambiguous; get_user_profile is clear

How to Write a Complete Tool Description

A Complete Tool Description Includes
  • What it does — Clear statement of the tool's purpose and action
  • When to use it — Scenarios that warrant calling this tool
  • What it returns — Format and structure of the output
  • Edge cases — What happens when input is invalid or data is not found
  • vs. similar tools — How to choose between this and related tools

Why the "vs. Similar Tools" Clause Matters Most

When you have multiple tools that could apply to similar situations, Claude needs explicit guidance on which to choose. The "vs. similar tools" clause is the most critical part of a description for disambiguation:

Example: Disambiguating Similar Tools

get_user: "...Use get_user for a single known user_id. Use find_users when searching by name/email with partial matches."

find_users: "...Use find_users when searching by name or email with partial matches. Use get_user when you already have the exact user_id."

Without these cross-references, Claude may call find_users when it already has the user_id, wasting a search operation.

Tool Use in Claude

Claude supports two categories of tools:

tool_choice modes control how Claude uses tools:

  • any — Claude must use at least one tool
  • tool — Claude must use a specific named tool

Part 06Error Handling Patterns

How to Handle Transient Failures

Transient failures are temporary and resolve on their own. They include network timeouts, 429 rate limits, 500 server errors, and 529 overloaded responses. The correct strategy is retry with exponential backoff:

Pythonimport time, anthropic def call_with_backoff(client, max_retries=3, **kwargs): for attempt in range(max_retries): try: return client.messages.create(**kwargs) except anthropic.RateLimitError: wait = 2 ** attempt # 1s, 2s, 4s time.sleep(wait) except anthropic.APIStatusError as e: if e.status_code >= 500: time.sleep(2 ** attempt) else: raise # 4xx = permanent, do not retry raise Exception("Max retries exceeded")

The official Python and TypeScript SDKs automatically retry 429 and 529 errors with exponential backoff. You only need custom retry logic for 500 errors.

How to Handle Validation Failures

When Claude sends invalid input to a tool (wrong data type, missing required field, out-of-range value), return is_error: true with a specific message about what is wrong and what is expected:

JSON{ "type": "tool_result", "tool_use_id": "toolu_01ABC...", "is_error": true, "content": "Validation error: 'max_results' must be an integer between 1 and 20. Received: 'fifty'. Please provide a numeric value within the valid range." }

The error message should tell Claude exactly how to fix the input so it can retry correctly.

How to Handle Business Logic Failures

When the operation is valid technically but not allowed by business rules (e.g., transferring more money than the account balance), return a clear explanation of why the operation was rejected:

JSON{ "type": "tool_result", "tool_use_id": "toolu_01DEF...", "is_error": true, "content": "Business rule violation: Cannot schedule appointment on Sunday. Business hours are Monday-Friday 9am-5pm. Please choose a weekday within business hours." }

How to Handle Permission Failures

When the agent lacks access to a resource, tell it what permission is needed, not just "access denied":

JSON{ "type": "tool_result", "tool_use_id": "toolu_01GHI...", "is_error": true, "content": "Permission denied: Current API token has 'read' scope. The 'delete_record' operation requires 'write' scope. Ask the user to provide a token with write permissions." }

Access Failure vs. Valid Empty Result

This is a critical distinction that Claude must be able to make. These two outcomes require completely different next steps:

ScenarioWhat HappenedClaude's Next Step
Access failure"You don't have access to this database"Report the access issue, ask user for credentials, try alternate data source
Valid empty result"The query returned no results" (0 rows)Report that no matching data exists, proceed with the task
Critical Distinction An access failure is NOT the same as an empty result. If Claude cannot tell the difference, it may tell the user "no data exists" when the real problem is that it does not have permission to see the data. Always use is_error: true for access failures and return a normal (non-error) result for valid empty queries.

How to Design Distinguishable Error Responses

Use structured error objects with typed fields so Claude can programmatically distinguish between error types:

JSON// Structured error response pattern { "error_type": "PERMISSION_DENIED", "message": "Cannot access table 'financials' with current credentials", "suggestion": "Request elevated access from the user or try the 'public_financials' table instead" } // vs. a valid empty result (NOT an error) { "results": [], "count": 0, "message": "No records match the query criteria" }

Error types to distinguish:

error_typeMeaningClaude's Action
TRANSIENTTemporary failure (network, rate limit)Retry the same operation
VALIDATIONInvalid input from ClaudeFix the input and retry
BUSINESS_RULEOperation not allowed by rulesExplain the constraint to the user
PERMISSION_DENIEDInsufficient accessAsk user for elevated access

Exam Tip Always use is_error: true for tool errors. The SDK auto-retries 429 and 529. The most critical distinction: access failure (is_error: true, need different credentials) vs. valid empty result (not an error, just no data). Use structured error objects with error_type, message, and suggestion.

Part 07MCP Configuration

What Goes in Project-Level MCP Config?

The project-level MCP configuration is stored in .mcp.json at the project root. It defines MCP servers that the whole team uses and is committed to git:

JSON — .mcp.json{ "mcpServers": { "jira": { "command": "npx", "args": ["-y", "@anthropic/mcp-server-jira"], "env": { "JIRA_URL": "https://team.atlassian.net" } }, "postgres": { "command": "npx", "args": ["-y", "@anthropic/mcp-server-postgres"], "env": { "DATABASE_URL": "postgresql://localhost:5432/mydb" } } } }

This file should contain shared team tools like project databases, issue trackers, and documentation servers. Do not put personal API keys here — use environment variables or user-level config.

What Goes in User-Level MCP Config?

User-level MCP configuration goes in ~/.claude/settings.json. It defines personal MCP servers like local dev tools and private API keys. This file is NOT committed to version control:

JSON — ~/.claude/settings.json{ "mcpServers": { "personal-notes": { "command": "npx", "args": ["-y", "@anthropic/mcp-server-filesystem"], "env": { "ROOT_DIR": "/home/user/notes" } } } }

How to Diagnose Missing MCP Server Access

When an MCP server's tools are not available, check this diagnostic checklist:

  1. Is the server URL/command correct? — Typos in the URL or command path
  2. Is the auth token valid? — Expired or incorrect credentials
  3. Is the tool in allowed_tools? — The tool_configuration may be blocking the tool
  4. Is the server running? — The MCP server process may have crashed or not started
  5. Check Claude Code logs — Run /mcp to see the status of connected MCP servers

Part 08Tool Scoping and Agent Roles

Why Too Many Tools Hurt Selection

Giving an agent too many tools causes multiple problems:

  • Higher token cost — Every tool definition is injected into the system prompt and consumes input tokens on every API call
  • More ambiguity — With many tools, Claude has more options to choose from, increasing the chance of misselection
  • Slower responses — More tool definitions mean more tokens to process
  • Higher misselection rate — Overlapping tool descriptions lead to the wrong tool being chosen

How Many Tools Each Agent Should Have

Rule of thumb: 5-15 tools per agent. If an agent needs more than 20 tools, consider:

  • Split into multiple specialized agents — A "code agent" and a "test agent" instead of one agent with all tools
  • Use tool_search — A meta-tool that searches for the right tool from a larger catalog
  • Use MCP with scoping — Connect to different MCP servers for different task types

Part 13 — Domain 4: Prompt Engineering and Structured OutputMatch Criteria and Few-Shot Examples

Introduction to Domain 4: Prompt Engineering and Structured Output

Domain 4 covers prompt engineering techniques for Claude: match criteria, few-shot examples, structured output, and common anti-patterns. Effective prompting is the difference between an agent that works reliably and one that produces inconsistent results.

Why "Only If You're Confident" Doesn't Work

A common anti-pattern is telling Claude "only do X if you're confident." This instruction is effectively meaningless because:

  • Claude does not have calibrated uncertainty — it does not "know" how confident it is
  • Claude is trained to be helpful, so it tends to be "confident" about most things
  • The instruction gives Claude no objective criteria for what qualifies as "confident"
  • Result: Claude will almost always proceed, making the guard effectively useless
Anti-Pattern vs. Correct Approach

WRONG: "Only flag this as a security issue if you're confident."

RIGHT: "Flag this as a security issue if the input contains SQL syntax (SELECT, INSERT, UPDATE, DELETE, DROP, UNION) AND the input is being passed directly to a database query without parameterization."

How to Write Explicit Match Criteria

Define exactly what qualifies as a match using objective, verifiable conditions:

  • Be specific: "Match if the input contains a date in YYYY-MM-DD format AND mentions a city name"
  • Use observable criteria: Properties that can be checked, not feelings
  • Combine conditions explicitly: Use AND/OR logic, not vague qualifiers

How to Define Non-Matches and Edge Cases

Equally important as defining matches is defining what does NOT qualify:

  • Explicit exclusions: "Do NOT match if the date is in the future"
  • Edge case handling: "Dates like '2024' alone without month/day are NOT matches"
  • Boundary conditions: "Empty strings, null values, and whitespace-only input should return 'no match'"

When to Reach for Few-Shot Examples

Use few-shot examples when:

  • Rules alone are ambiguous — The criteria are hard to express precisely in words
  • Output format matters — Showing the exact expected format is clearer than describing it
  • Edge cases are hard to describe — Examples demonstrate the correct handling better than rules
  • Consistency is critical — Examples establish a concrete pattern to follow

How Many Few-Shot Examples to Use

3-5 examples for most tasks. At minimum, include:

  • 1 positive match — A clear example of input that should match
  • 1 negative match — A clear example of input that should NOT match
  • 1 edge case — A tricky input that tests the boundary conditions
XML Tags<examples> <example type="positive"> <input>2024-03-15 event in Paris</input> <output>match: true (date: 2024-03-15, city: Paris)</output> </example> <example type="negative"> <input>meeting next Tuesday</input> <output>match: false (no YYYY-MM-DD date found)</output> </example> <example type="edge-case"> <input>2024 conference</input> <output>match: false (year-only is not a valid YYYY-MM-DD date)</output> </example> </examples>

Showing Reasoning in Examples

Include the reasoning process in your few-shot examples, not just the answer. This teaches Claude how to think about matching, not just what the output should be:

Example with Reasoning<example> <input>2024-03-15 event in Paris</input> <reasoning> Contains "2024-03-15" which is YYYY-MM-DD format. ✓ Contains "Paris" which is a city name. ✓ Both criteria met. </reasoning> <output>match: true</output> </example>

How Prompting Works in Claude

Claude processes prompts in a specific priority order:

  • System prompt — highest authority, persistent behavior rules
  • Tool descriptions — guide tool selection and usage
  • Few-shot examples — demonstrate expected patterns
  • User message — the specific request to handle

Match criteria should be in the system prompt (always present) while examples go in user context or cached prompt blocks. This separation ensures criteria aren't diluted by conversation history.

Exam Tip "Only if you're confident" is an anti-pattern — it does nothing because Claude lacks calibrated uncertainty. Replace with explicit, observable match criteria. Show reasoning in examples, not just answers. Use 3-5 few-shot examples with at least one positive, one negative, and one edge case.

Guaranteed Schema Conformance

The Messages API supports output_config.format with a JSON Schema, guaranteeing that the model's output conforms to the specified schema. This eliminates parsing errors and post-processing validation.

Setting strict: true on a tool definition ensures that Claude's tool call parameters exactly match the JSON Schema, with no extra fields:

JSON{ "name": "create_ticket", "description": "Create a support ticket", "strict": true, "input_schema": { "type": "object", "properties": { ... }, "required": [...], "additionalProperties": false } }

Supported JSON Schema Features

Supported

object, array, string, number, boolean, null, enum, const, anyOf, allOf, $ref/$defs

Preventing Syntax Errors with JSON Schema

Without structured output, Claude generates free-form text that might be valid JSON. With output_config.format, the grammar engine guarantees syntactically correct output — no missing commas, no trailing brackets, no unquoted keys. The schema acts as a parser constraint during generation.

Handling Fabricated Data and Empty Fields

Even with schema conformance, Claude may fabricate values to fill required fields. Mitigations:

  • Use nullable types for fields that might not have data: "type": ["string", "null"]
  • Add instructions: "Return null for any field you cannot determine from the input"
  • Validate outputs against source data, not just schema

Using Optional, Nullable Fields, and Enum Values

  • Optional fields: Omit from required array — Claude may or may not include them
  • Nullable: "type": ["string", "null"] — field is present but value can be null
  • Enum: "enum": ["low", "medium", "high"] — restricts to exact values, prevents hallucinated categories
  • Const: "const": "v1" — forces a fixed value (useful for schema versioning)

Retry-with-Error-Feedback Technique

When structured output fails validation (business logic, not syntax), use this pattern:

  1. Get initial response with structured output
  2. Run your business validation on the parsed result
  3. If validation fails, send a follow-up message with the error: "The previous output had these issues: [errors]. Please fix and regenerate."
  4. Include the original output and specific error details in the retry

Limitations

  • No recursive schemas
  • No min/max constraints (minLength, maxLength, minimum, maximum)
  • additionalProperties: false is required on all objects
  • First request with a new schema has higher latency (grammar compilation); compiled grammars are cached for 24 hours
Exam Tip Structured output prevents syntax errors but NOT fabricated data — validate business logic separately. Use nullable fields + "return null if unknown" instruction to prevent fabrication. The retry-with-error-feedback technique handles validation failures. additionalProperties: false is required.

Progressive Summarization and Detail Loss

Progressive summarization replaces older conversation turns with increasingly compressed summaries. The trade-off: each compression round loses some detail. Strategies to minimize loss:

  • Summarize observations aggressively (tool output details)
  • Preserve decisions and reasoning verbatim (why something was done)
  • Keep current task state at full fidelity
  • Use structured summaries: "Completed: X. Found: Y. Still needed: Z."

Case-Facts Blocks

A case-facts block is a structured summary placed at the top of context containing the essential facts about the current task. This ensures critical information is never lost to summarization:

The "Lost in the Middle" Problem

LLMs attend most strongly to the beginning and end of the context window, with weaker attention to content in the middle. This means:

  • Instructions at the start (system prompt) and end (latest user message) are most reliably followed
  • Information buried in the middle of a long conversation may be overlooked
  • Fix: Place key findings at the top of tool results, not buried in verbose output

Placing Key Findings at the Top

When returning tool results, structure them with the most important information first:

  • Lead with the answer: "Found 3 security vulnerabilities" before listing details
  • Summary before details: Brief conclusion, then supporting evidence
  • Use structured tags: <finding>, <summary>, <details> to separate importance levels

Using Structured Tags and Trimming Verbose Results

Wrap tool outputs in XML tags so the agent can selectively attend to important parts. Trim verbose outputs before returning:

  • Log files: return only ERROR/WARNING lines, not full logs
  • API responses: extract relevant fields, drop metadata
  • Search results: return top-N matches with snippets, not full documents

Context Rot

Context rot is the degradation of model accuracy as the context window fills. Even though the model can technically handle 1M tokens, performance degrades as more content is added.

Compaction

Claude Code supports server-side auto-summarization (compaction) when the conversation approaches the context limit. The system automatically summarizes older parts of the conversation to free up space while preserving the most important information.

Management Strategies

Summarize History

Periodically replace old conversation turns with a summary. Keep recent turns verbatim, summarize older ones.

Drop Old Tool Results

Replace large tool results from earlier turns with a brief summary of what was found.

Use Compaction

Rely on server-side compaction for long-running sessions. The system handles summarization automatically.

Memory Tool

For multi-session work, use the memory tool to persist important context across sessions rather than keeping it in the window.

  • Input too large — 400 error before processing even begins

Structured Error Context in Multi-Agent Systems

In hub-spoke architectures, errors must flow back to the coordinator with enough context to make decisions. Structure error responses as objects, not strings:

JSON — Structured Error{ "status": "error", "error_type": "timeout", "attempted": "Query users table for active subscriptions", "details": "Connection timeout after 5000ms to db.example.com:5432", "retry_count": 2, "max_retries": 3, "alternatives": ["Try read replica", "Use cached data (15min stale)"] }

Importance of Alternative Approaches

When a tool fails, suggest alternatives in the error response. This is critical because:

  • Claude can choose the best alternative without human intervention
  • Prevents the agent from getting stuck in a retry loop on a permanently broken path
  • Enables graceful degradation: "Primary DB unavailable → use cached data → inform user data may be stale"

  • D Exhausting retries is too expensive in terms of API calls and token costs, since each retry consumes a full round-trip of input and output tokens
Correct: B. Waiting until retries are exhausted before reporting is a "silent failure" anti-pattern. The coordinator has no visibility into what is happening and cannot intervene — it might switch to an alternative sub-agent, try a different approach, or inform the user about a delay. Errors should be propagated immediately with context about retry state ("attempt 1/3 failed, retrying"). This lets the coordinator make architecture-level decisions (failover, parallelization) instead of waiting blindly for a sub-agent that may be stuck in a retry loop.
