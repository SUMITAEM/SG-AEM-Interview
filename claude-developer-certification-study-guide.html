Part 01Agents and Workflows

What Are AI Agents?

AI agents are autonomous systems that combine Large Language Models (LLMs) with tools and external data to accomplish tasks. Unlike a simple prompt-in/text-out flow, an agent operates in a loop: it reasons about a task, decides which tool to call, executes the tool, reads the result, and then reasons again until the task is complete.

Key Agent Characteristics
  • Autonomy — The agent decides its own next step rather than following a fixed script
  • Tool use — Agents call functions (search, code execution, file I/O) to interact with the world
  • Iterative reasoning — Each tool result feeds back into the LLM for the next decision
  • Goal-directed — The agent works toward completing a user-defined objective

Managed Agents Core Concepts

Managed Agents (CMA) use four key abstractions:

  • Agent — A configuration defining the model, system prompt, tools, and MCP servers. Created once, reused across sessions.
  • Environment — An isolated sandbox (filesystem, network) where the agent runs. Persistent between sessions.
  • Session — A single conversation with an agent in an environment. Contains the message history.
  • Events — Messages sent to/from the session. User events trigger agent processing; agent events stream back results.

The Agentic Loop Pattern

Whether you use the Messages API, Agent SDK, or Managed Agents, the core pattern is the same agentic loop:

Pythonimport anthropic client = anthropic.Anthropic() messages = [{"role": "user", "content": "What is the weather in San Francisco?"}] tools = [{ "name": "get_weather", "description": "Get current weather for a city", "input_schema": { "type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"] } }] # Agentic loop: keep going until no more tool calls while True: response = client.messages.create( model="claude-sonnet-5", max_tokens=1024, tools=tools, messages=messages ) # If the model stopped normally, we are done if response.stop_reason == "end_turn": print(response.content[0].text) break # If the model wants to call a tool, execute it if response.stop_reason == "tool_use": tool_block = next(b for b in response.content if b.type == "tool_use") result = execute_tool(tool_block.name, tool_block.input) # Append assistant response + tool result, then loop messages.append({"role": "assistant", "content": response.content}) messages.append({"role": "user", "content": [{ "type": "tool_result", "tool_use_id": tool_block.id, "content": result }]})

Workflow Patterns

Workflows are deterministic, multi-step orchestrations. Unlike agents (open-ended), workflows follow a predefined flow.

Sequential (Prompt Chaining)

Output of step N becomes input to step N+1. Example: Extract data → Validate → Format → Respond.

Parallel (Fan-Out)

Same input sent to multiple models/prompts simultaneously. Results aggregated. Example: Translate into 5 languages at once.

Router

Classifier determines which specialized handler processes the input. Example: Classify ticket → route to billing/technical/general handler.

Orchestrator-Workers

Central LLM breaks task into subtasks and delegates to worker agents. Example: "Refactor this codebase" → split into file-level tasks.

Exam Tip: Agents vs. Workflows Use agents for open-ended tasks where the number of steps is unknown (research, coding, debugging). Use workflows for deterministic multi-step processes where each step is predefined (data pipelines, content moderation, classification chains).

Agent SDK Overview

The Claude Agent SDK is a separate package (claude-agent-sdk) that provides the full Claude Code harness—the agent loop, built-in tools (file I/O, bash, grep), and tool execution—in a process you operate on your own infrastructure. It sits between the raw Messages API and fully Managed Agents.

Part 02Requirements and Lifecycle

AI Application Development Lifecycle

Building production AI applications follows an iterative lifecycle, not a waterfall. Each phase feeds back into the others:

The Seven Phases
  1. Define Requirements — What must the system do? What are success criteria?
  2. Design — Choose models, architect prompts, define tool schemas
  3. Implement — Build the application, integrate APIs, wire up tools
  4. Test / Evaluate — Run evals, measure against criteria, identify gaps
  5. Deploy — Ship to production with monitoring and fallbacks
  6. Monitor — Track accuracy, latency, cost, user feedback in production
  7. Iterate — Refine prompts, adjust models, expand capabilities based on data

Defining Success Criteria (SMART)

Vague goals lead to unmeasurable systems. Every AI project needs SMART criteria:

LetterMeaningBad ExampleGood Example
SSpecific"Classify sentiments well""Classify tweets as positive/negative/neutral"
MMeasurable"High accuracy""Achieve F1 ≥ 0.85 on 10,000 labeled posts"
AAchievable"100% accuracy on all inputs""95% accuracy on in-distribution test set"
RRelevant"Fast response""p95 latency < 2 seconds for user-facing flow"
TTime-bound"Eventually""Within 2-week sprint cycle"

Requirements Categories

Eight Requirement Dimensions for AI Applications
  • Task Fidelity — Does the output correctly accomplish the task?
  • Consistency — Same input produces reliably similar outputs
  • Relevance — Output addresses the actual question/need
  • Tone / Style — Matches brand voice and audience expectations
  • Privacy — PII handling, data retention, compliance requirements
  • Context Utilization — Makes full use of provided context without hallucinating beyond it
  • Latency — Time to first token and total response time
  • Cost — Token costs, API call volume, infrastructure overhead

The Iteration Loop

AI application development is fundamentally iterative. The core loop is:

  1. Define criteria — What does success look like? (measurable metrics)
  2. Build evals — Create test cases that measure those criteria
  3. Draft prompt — Write the initial system prompt and user prompt template
  4. Test — Run evals against the prompt
  5. Analyze — Examine failures, identify patterns
  6. Refine — Update prompts, model selection, or architecture based on findings

Versioning and Monitoring

  • Version prompts — Treat prompts like code: store in version control, tag releases, track changes over time
  • Version configurations — Model selection, temperature, max_tokens, tool definitions should all be versioned alongside prompts
  • Production monitoring — Track accuracy (via user feedback or automated checks), latency (p50/p95/p99), cost (tokens per request), error rates, and refusal rates
Exam Tip The exam tests whether you know the correct order of the lifecycle and the importance of defining measurable criteria BEFORE building. "Build evals before building the product" is a key Anthropic best practice.

Stop Reasons

Stop Reasons and Their Meanings
  • end_turn — Model finished its response naturally
  • max_tokens — Hit the max_tokens limit (output was truncated)
  • stop_sequence — Model generated one of the custom stop sequences
  • tool_use — Model wants to call a tool (continue the agentic loop)
  • refusal — Model declined to respond (check stop_details.category)
  • model_context_window_exceeded — Output generation exceeded the context window

Streaming

Set stream: true to receive Server-Sent Events (SSE). Events flow in this order:

  1. message_start — Opening message metadata
  2. content_block_start — Beginning of a content block
  3. content_block_delta — Incremental text/tool chunks
  4. content_block_stop — End of a content block
  5. message_delta — Final stop_reason and usage stats
  6. message_stop — Stream complete
Python Streamingwith client.messages.stream( model="claude-sonnet-5", max_tokens=1024, messages=[{"role": "user", "content": "Tell me a story"}] ) as stream: for text in stream.text_stream: print(text, end="", flush=True)

Authentication

  • x-api-key header with your API key
  • anthropic-version header (required for raw HTTP calls)
  • ANTHROPIC_API_KEY environment variable (auto-detected by SDKs)
  • Official SDKs available in: Python, TypeScript, Go, Java, C#, PHP, Ruby

Part 05Software Engineering Foundations

SE Principles Applied to AI Applications

Building with LLMs does not exempt you from software engineering fundamentals. In fact, the non-deterministic nature of AI makes these practices even more critical.

Version Control for Prompts

  • Store prompts in version control (Git), not in application code as inline strings
  • Use a dedicated directory (e.g., prompts/) with versioned files
  • Tag releases so you can roll back to a known-good prompt version
  • Track prompt changes with the same rigor as code changes: PRs, reviews, changelogs

Separation of Concerns

  • Separate prompts from application logic — prompts are configuration, not code
  • Externalize model selection and parameters (temperature, max_tokens) into config files
  • Use dependency injection for the API client so you can mock it in tests

Error Handling Patterns

Pythonimport anthropic import time def call_with_retry(client, max_retries=3, **kwargs): """Retry with exponential backoff for transient errors.""" for attempt in range(max_retries): try: return client.messages.create(**kwargs) except anthropic.RateLimitError: wait = 2 ** attempt # 1s, 2s, 4s time.sleep(wait) except anthropic.APIStatusError as e: if e.status_code >= 500: # Server error, retry time.sleep(2 ** attempt) else: raise # Client error (4xx), do not retry raise Exception("Max retries exceeded")

Design Patterns for Claude Applications

Well-designed Claude applications separate concerns into distinct layers:

Prompt Layer

System prompts, user prompt templates, few-shot examples. Versioned and configurable.

API Layer

SDK client, retry logic, streaming handling, error mapping. Infrastructure code.

Business Logic Layer

Application-specific rules, validation, post-processing, response formatting.

System Prompt Design

The system prompt is the most important design element. It defines the model's role, behavior, constraints, and output format:

Pythonsystem_prompt = """You are a senior software engineer reviewing code for security vulnerabilities. <instructions> - Focus on OWASP Top 10 vulnerabilities - Rate each finding as Critical, High, Medium, or Low severity - Provide specific remediation advice for each finding - If no vulnerabilities are found, explicitly state the code is clean </instructions> <output_format> Return a JSON array of findings, each with: file, line, severity, description, remediation </output_format>"""

Designing for Reliability

  • Handle all stop reasons — Check for refusal, max_tokens truncation, and context overflow
  • Fallback strategies — Try a different model if the primary model refuses or errors
  • Idempotency — Design tool executions to be safely retryable
  • Timeout handling — Set appropriate timeouts and handle them gracefully

Designing for Cost

  • Use the cheapest model that meets quality requirements for each task
  • Minimize token usage: shorter prompts, concise examples, avoid redundancy
  • Use streaming for perceived speed improvement without increasing cost
  • Implement prompt caching for system prompts and repeated context

User Experience Design

  • Streaming — Show tokens as they arrive for perceived speed
  • Progress indicators — For agentic tasks, show which tool is being called
  • Graceful degradation — If Claude refuses or errors, provide helpful fallback messaging
  • Confidence signals — Let users know when the model is uncertain
Exam Tip The Messages API is stateless (you manage history). Managed Agents are stateful (server manages sessions). This distinction affects architecture decisions around state management, scaling, and cost.

Part 09Eval, Testing, and Debugging

Five Evaluation Types

Evaluations measure whether your AI application meets its success criteria. Each type suits different output characteristics:

1. Exact Match (Categorical Outputs)

Pythondef eval_exact_match(predictions, ground_truth): """For classification tasks: accuracy = correct / total""" correct = sum(1 for p, g in zip(predictions, ground_truth) if p == g) return correct / len(ground_truth) # Example: Sentiment classification predictions = ["positive", "negative", "neutral"] ground_truth = ["positive", "negative", "positive"] accuracy = eval_exact_match(predictions, ground_truth) # 0.667

2. Cosine Similarity (Semantic Similarity)

Pythonfrom sentence_transformers import SentenceTransformer from sklearn.metrics.pairwise import cosine_similarity model = SentenceTransformer("all-MiniLM-L6-v2") def eval_cosine(generated, reference): """Semantic similarity using SBERT embeddings.""" emb_gen = model.encode([generated]) emb_ref = model.encode([reference]) return cosine_similarity(emb_gen, emb_ref)[0][0] score = eval_cosine( "The cat sat on the mat", "A feline rested on the rug" ) # ~0.78 (semantically similar)

3. ROUGE-L (Summarization Quality)

Pythonfrom rouge_score import rouge_scorer scorer = rouge_scorer.RougeScorer(["rougeL"], use_stemmer=True) def eval_rouge_l(generated, reference): """ROUGE-L: longest common subsequence ratio.""" scores = scorer.score(reference, generated) return scores["rougeL"].fmeasure score = eval_rouge_l( "The quick brown fox jumps over the lazy dog", "A fast brown fox leaps over a sleepy dog" ) # ~0.60

4. LLM-Based Likert Scale (Subjective Quality)

Pythondef eval_llm_likert(client, generated_response, criteria): """Use a DIFFERENT model to rate quality 1-5.""" response = client.messages.create( model="claude-haiku-4-5", # Different from the generator! max_tokens=100, messages=[{ "role": "user", "content": f"""Rate this response on a 1-5 scale for: {criteria} Response: {generated_response} Return ONLY a number 1-5.""" }] ) return int(response.content[0].text.strip())

5. LLM-Based Binary Classification (Safety/Compliance)

Pythondef eval_safety_check(client, response_text): """Binary check: does the response contain PII?""" result = client.messages.create( model="claude-haiku-4-5", max_tokens=10, messages=[{ "role": "user", "content": f"""Does this response contain any PII (names, emails, phone numbers, addresses)? Response: {response_text} Answer ONLY 'yes' or 'no'.""" }] ) return response.content[0].text.strip().lower() == "no"
Best Practice: Use a Different Model to Evaluate

Always use a different model to evaluate than the one generating the output. This avoids self-evaluation bias. For example, generate with Sonnet 5, evaluate with Haiku 4.5 (or vice versa).

Debugging Techniques

  • Examine thinking blocks — Enable extended thinking to see the model's reasoning process
  • Check stop_reason — Was the output truncated (max_tokens)? Refused (refusal)?
  • Token counting API — Validate input size before sending (pre-flight check)
  • Add logging — Log full request/response pairs (redact sensitive data) for debugging
  • Regression tests — Save "golden outputs" and compare on prompt changes

Edge Cases to Test

  • Sarcasm and irony in sentiment analysis
  • Typos and misspellings in user input
  • Very long inputs that approach context limits
  • Ambiguous queries with multiple valid interpretations
  • Adversarial inputs (prompt injection attempts)
  • Empty inputs and boundary conditions
Exam Tip Know all five eval types and when to use each. Exact match for classification, cosine similarity for semantic comparison, ROUGE-L for summarization, Likert for subjective quality, binary classification for safety checks.

Part 10Large Language Models (LLMs) and Technical Fundamentals

What is an LLM?

A Large Language Model is a neural network trained on massive text datasets to predict the next token in a sequence. The "large" refers to both the training data (trillions of tokens) and the model parameters (billions to trillions).

Transformer Architecture

  • Self-attention — Mechanism that allows each token to "attend to" every other token in the sequence, capturing long-range dependencies
  • Multi-head attention — Multiple parallel attention computations, each learning different relationship patterns
  • Feed-forward layers — Dense layers between attention blocks that transform representations
  • Layer normalization — Stabilizes training by normalizing intermediate representations

Tokenization

Token Estimation Rules
  • ~4 characters per token (English text)
  • ~0.75 words per token (English text)
  • 1 token ~ 1 word for short common words
  • Long or uncommon words may be 2-4 tokens
  • Code tends to use more tokens per character than prose
  • Claude 4.7+ new tokenizer: ~30% more tokens for the same text compared to older tokenizers

Training Process

  1. Pre-training — Train on massive text corpora to learn language patterns (unsupervised)
  2. Fine-tuning — Train on curated instruction-following examples (supervised)
  3. RLHF — Reinforcement Learning from Human Feedback to align with human preferences
  4. Constitutional AI (CAI) — Anthropic's approach: model self-critiques against a constitution of principles

Prompt Caching Deep Dive

Prompt caching stores and reuses the prefix of your request across API calls. It can reduce costs by up to 90% on cache hits.

How It Works

  • Automatic caching — The API automatically caches repeated prefixes without explicit configuration
  • Explicit caching — Mark content blocks with cache_control: {"type": "ephemeral"} for precise control
  • TTL — 5-minute default, 1-hour extended (higher write cost)
  • Minimum tokens — Varies by model (1024 for Sonnet/Haiku, 2048 for Opus, 4096 for Fable)

Python# Pre-warm cache with max_tokens: 0 (no output generated) client.messages.create( model="claude-sonnet-5", max_tokens=0, system=[{ "type": "text", "text": large_system_prompt, "cache_control": {"type": "ephemeral"} }], messages=[{"role": "user", "content": "."}] ) # Subsequent calls with the same prefix get 0.1x pricing

Cache Invalidation Hierarchy

The cache prefix must match exactly from the beginning. Changes invalidate everything after the change point:

  1. Tools — Changing any tool definition invalidates the entire cache
  2. System prompt — Changing the system prompt invalidates system + messages cache
  3. Messages — Only new messages at the end are uncached; earlier messages stay cached
Cache-Aware ITPM Cached tokens do NOT count toward your input tokens per minute (ITPM) rate limit. This means cached requests can run at much higher throughput than uncached ones.

Context Window = Working Memory, NOT Training Data

The context window is the total capacity for a single conversation. It is not the model's "knowledge" from training. A 1M token context window means you can pass up to 1M tokens of input + output in one request—it does not mean the model was trained on only 1M tokens.

What Counts Toward the Context Window

  • System prompt — Counted as input tokens
  • All messages — Every user and assistant message in the conversation history
  • Tool definitions — JSON schemas for all defined tools
  • Tool results — Return values from tool calls
  • Images — Converted to tokens based on resolution
  • Thinking blocks — Extended thinking tokens count toward max_tokens AND context
  • Output — Generated text also occupies the context window

Context Rot

Context rot refers to the degradation of output quality as the context window fills up. Models may lose track of earlier context or become less coherent with very long conversations. Strategies to mitigate:

  • Summarize and compact older messages
  • Remove completed tool results that are no longer relevant
  • Place the most important information at the beginning and end of the context (primacy and recency effects)

Context Awareness

Some models (Sonnet 5, Sonnet 4.6, Haiku 4.5) are context-aware — they can track their remaining token budget and adapt behavior (e.g., producing shorter responses as the window fills).

Server-Side Compaction

For Managed Agents, Anthropic automatically compacts (summarizes) earlier conversation when tokens approach the context limit. For the Messages API, you must implement compaction yourself.

Context Window Overflow

  • Input overflow — Returns a 400 error if input exceeds the model's context window
  • Output overflow — Returns stop_reason: "model_context_window_exceeded" if output generation would exceed the window

Long-Context Best Practices

  • Documents before queries — Place reference documents in the system prompt or early messages, then ask questions after
  • Use XML tags — Structure long context with clear section markers
  • Curate context — Only include information relevant to the current task; more is not always better
  • Index attributes — Add metadata (file names, document titles) to help the model locate relevant sections

Prompt Caching and Context

Cached prefixes still occupy the context window. Caching changes the cost (0.1x on hits), not the size. A 500K cached system prompt still uses 500K tokens of your 1M context window.

Memory Tool

For multi-session state (remembering information across separate conversations), Claude's built-in memory tool provides persistent key-value storage that survives session boundaries.

Exam Tip The number one mistake: confusing context window with training data. Context = working memory for one conversation. Training data = what the model learned during training. Also remember: cached tokens reduce cost but still use context space.

Part 14Prompt Engineering

Five Core Principles

Effective prompts follow five core principles, remembered with the mnemonic CERRS:

Clear and Direct

Be explicit about what you want. Avoid ambiguity. State constraints and requirements directly.

Examples (Few-Shot)

Provide 3-5 diverse, relevant examples wrapped in example tags. Show edge cases.

Role Prompting

Set the model's role in the system prompt. Even one sentence makes a measurable difference.

Reasoning (Chain of Thought)

Ask the model to think step by step. Use extended thinking for complex reasoning tasks.

Structure (XML Tags)

Use XML tags to organize prompts: <instructions>, <context>, <input>, <output>, <example>.

The Golden Rule

"Could a colleague with minimal context follow this prompt?"

If you showed your prompt to a colleague with no project background, could they produce the output you expect? If not, add more context, examples, or constraints.
