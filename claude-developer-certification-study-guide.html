Part 01Agents and Workflows

Introduction to the Hub-Spoke Model

The hub-spoke model is the most common architecture for multi-agent systems. A central orchestrator (the hub) delegates discrete subtasks to specialized worker agents (the spokes). Communication is one-way: the orchestrator sends tasks to workers and receives results back, but workers never communicate directly with each other.

  • The orchestrator holds the full context and decides which worker to invoke
  • Workers are specialized — each handles one domain (code, search, data analysis)
  • One-way communication keeps the architecture simple and predictable
  • Workers can run in parallel since they are independent of each other

What Is the Agentic Loop?

The agentic loop is the core execution pattern that makes an AI agent autonomous. It follows a strict cycle:

  1. Request — User sends a message to the model
  2. Reason — Model analyzes the task and decides next steps
  3. tool_use — Model emits a tool call block (stop_reason: "tool_use")
  4. Execute — Your code runs the tool and collects the result
  5. tool_result — You send the result back to the model in a tool_result block
  6. Reason — Model processes the result and decides whether to call another tool or respond
  7. Response — When stop_reason is "end_turn", the loop terminates
Python# The agentic loop: keep calling until stop_reason == "end_turn" while True: response = client.messages.create( model="claude-sonnet-5", max_tokens=4096, tools=tools, messages=messages ) if response.stop_reason == "end_turn": print(response.content[0].text) break if response.stop_reason == "tool_use": # Extract all tool_use blocks, execute each, append results tool_blocks = [b for b in response.content if b.type == "tool_use"] messages.append({"role": "assistant", "content": response.content}) tool_results = [] for tb in tool_blocks: result = execute_tool(tb.name, tb.input) tool_results.append({"type": "tool_result", "tool_use_id": tb.id, "content": result}) messages.append({"role": "user", "content": tool_results})

Introduction to Tool Call Interception Hooks

Hooks are shell commands configured in settings.json that run deterministically before or after tool execution. They are not prompts — they are actual code that Claude cannot override.

  • PreToolUse — Runs before a tool executes. Can block, modify, or allow the call.
  • PostToolUse — Runs after a tool executes. Can validate output, run tests, or log actions.

Hooks receive the tool name and arguments as JSON on stdin and return a JSON response indicating whether to proceed, block, or modify.

How to Branch on tool_use

In your agentic loop code, you must check the stop_reason field of every API response to decide what to do next:

  • If stop_reason == "tool_use": extract all tool_use blocks from response.content, execute each tool, and append the results
  • If stop_reason == "end_turn": the model is done — extract the text response and break the loop
  • If stop_reason == "max_tokens": the output was truncated — handle gracefully

How a Coordinator Decomposes Tasks

A coordinator (orchestrator) agent breaks a complex task into discrete subtasks and assigns each to a specialized worker:

  1. Analyze — Understand the full task and identify component parts
  2. Decompose — Split into discrete, independent subtasks
  3. Assign — Route each subtask to the most capable worker agent
  4. Monitor — Track progress and handle failures
  5. Aggregate — Combine worker outputs into a coherent final result

Agentic AI vs Generative AI

Generative AI

Creates content from prompts: text, images, code. Single-turn input/output. No tool use, no planning, no iteration. Example: "Write a poem about cats."

Agentic AI

Autonomously plans, uses tools, takes actions, and iterates. Multi-turn loops with goal tracking. Agentic = Generative + Tools + Loops + Goals. Example: "Research and fix the bug in my codebase."

The Architecture of Agentic AI

An agentic AI system consists of five core components working together:

  • LLM Brain — The reasoning engine that decides what to do next
  • Tool Access — Functions the agent can call (search, file I/O, code execution, APIs)
  • Memory — Short-term (conversation history) and long-term (vector stores, databases)
  • Planning Loop — The agentic loop that iterates until the task is complete
  • Goal Tracking — Awareness of the overall objective and progress toward it

Types of Agentic AI

  • Simple tool-calling agents — Single LLM with tool access, one loop iteration at a time
  • ReAct agents — Reason-Act-Observe pattern: think, act, observe result, repeat
  • Plan-and-execute agents — Create a plan first, then execute each step sequentially
  • Multi-agent systems — Multiple specialized agents collaborating on complex tasks
  • Autonomous agents — Minimal human oversight, self-directed goal pursuit over long horizons

Multi-Agent Systems: When AI Agents Work Together

When tasks are too complex for a single agent, multiple agents collaborate. Four common patterns:

Hub-Spoke

Central orchestrator delegates to specialized workers. One-way communication. Most common pattern.

Peer-to-Peer

Agents communicate directly with each other. No central coordinator. Good for collaborative tasks.

Hierarchical

Manager agents delegate to sub-manager agents, who delegate to worker agents. For very complex tasks.

Collaborative

Agents share a workspace and build on each other's outputs. Good for creative tasks like writing or design.

Memory and Context in AI Agents

  • Short-term memory — Conversation history within the context window. Lost when the session ends.
  • Long-term memory — Persisted across sessions via memory tools, vector stores, or databases. Claude Code uses ~/.claude/memory for auto-memories.
  • Working memory — Thinking blocks where the model reasons through a problem before responding. Visible via extended thinking.

What Is AWS Strands Agents?

AWS Strands Agents is an open-source framework from AWS for building AI agents. Key characteristics:

  • Model-agnostic — Works with Claude, GPT, and other models via Amazon Bedrock
  • Tool-first design — Define tools as Python functions with decorators, the framework handles the loop
  • AWS ecosystem integration — Native support for Lambda, DynamoDB, S3, and other AWS services
  • Lightweight — Minimal boilerplate; focuses on simplicity over framework features

What Is LangGraph?

LangGraph is a framework for building stateful, multi-step agent workflows as directed graphs:

  • Nodes are processing steps (LLM calls, tool executions, data transformations)
  • Edges are transitions between steps (conditional routing, loops)
  • Supports cycles — unlike simple chains, graphs can loop back for iterative processing
  • Checkpointing — save and resume state, time-travel debugging
  • Part of the LangChain ecosystem but can be used independently

Workflow Patterns

Workflows are deterministic, multi-step orchestrations. Unlike agents (open-ended), workflows follow a predefined flow:

Sequential (Prompt Chaining)

Output of step N becomes input to step N+1. Example: Extract data → Validate → Format → Respond.

Parallel (Fan-Out)

Same input sent to multiple models/prompts simultaneously. Results aggregated. Example: Translate into 5 languages at once.

Router

Classifier determines which specialized handler processes the input. Example: Classify ticket → route to billing/technical/general handler.

Orchestrator-Workers

Central LLM breaks task into subtasks and delegates to worker agents. Example: "Refactor this codebase" → split into file-level tasks.

Part 02Requirements and Lifecycle

What Are Functional vs Infrastructure Requirements?

Functional Requirements

What the app should DO:

  • Classify support tickets into categories
  • Summarize documents into bullet points
  • Answer questions from a knowledge base
  • Extract structured data from unstructured text
Infrastructure Requirements

How the app runs:

  • Latency targets (p95 < 2s)
  • Throughput (1000 requests/minute)
  • Availability (99.9% uptime)
  • Cost budgets ($500/month API spend)
  • Security and compliance (SOC 2, HIPAA)

What Is the Software Development Lifecycle (SDLC)?

The SDLC for AI applications follows seven iterative phases:

  1. Plan — Define requirements, success criteria, and constraints
  2. Design — Choose models, architect prompts, define tool schemas, plan data flow
  3. Implement — Build the application, integrate APIs, wire up tools
  4. Test — Run evals, measure accuracy, check edge cases, validate security
  5. Deploy — Ship to production with monitoring, fallbacks, and canary rollouts
  6. Monitor — Track accuracy, latency, cost, error rates, user feedback in production
  7. Iterate — Refine prompts, adjust models, expand capabilities based on data

Gathering Functional and Infrastructure Requirements

  • Interview stakeholders — Understand what users need the system to do and their expectations for quality
  • Define success criteria — SMART criteria: Specific, Measurable, Achievable, Relevant, Time-bound
  • Set SLAs — Define latency targets, uptime requirements, error budgets
  • Estimate token budgets — Calculate expected input/output tokens per request, multiply by volume, factor in caching
  • Identify constraints — Data residency, compliance, model availability, rate limits

Managing a Claude App Across the SDLC

  • Prompt versioning — Store prompts in Git, tag releases, diff changes between versions
  • Eval pipelines — Automated tests that run on every prompt change to catch regressions
  • Model migration — When Anthropic releases new models, test with evals before switching. Pin to specific model versions for stability.
  • Monitoring production quality — Track accuracy, latency, cost, refusal rates. Set alerts for regressions. Use LangSmith or custom dashboards.
Exam Tip The exam tests whether you distinguish functional requirements (WHAT it does) from infrastructure requirements (HOW it runs). "Build evals before building the product" is a key Anthropic best practice.

What Is the Claude Messages API?

The Claude Messages API is the HTTP API for sending messages to Claude. Everything goes through POST /v1/messages. Three parameters are required: model, max_tokens, and messages. Tools, structured outputs, thinking, caching, and streaming are all features of this single endpoint.

What Is Streaming in the Claude API?

Streaming delivers tokens as they are generated via Server-Sent Events (SSE). Events flow in this order:

  1. message_start — Opening message metadata
  2. content_block_start — Beginning of a content block
  3. content_block_delta — Incremental text/tool chunks
  4. content_block_stop — End of a content block
  5. message_delta — Final stop_reason and usage stats
  6. message_stop — Stream complete
Python Streamingwith client.messages.stream( model="claude-sonnet-5", max_tokens=1024, messages=[{"role": "user", "content": "Tell me a story"}] ) as stream: for text in stream.text_stream: print(text, end="", flush=True)
TypeScript Streamingconst stream = client.messages.stream({ model: "claude-sonnet-5", max_tokens: 1024, messages: [{ role: "user", content: "Tell me a story" }] }); stream.on("text", (text) => process.stdout.write(text));

What Are Vision and Multi-Format Inputs?

Claude supports images and documents as input content blocks:

  • Image sources: base64 (inline), url (fetched by API), file_id (uploaded file)
  • Formats: JPEG, PNG, GIF, WebP
  • Placement: Place images before text in the message for best results
  • Visual tokens: Calculated as ceil(width/28) * ceil(height/28)
  • PDF support: Documents can be sent as document content blocks for analysis

What Is Extended Thinking?

Extended thinking lets Claude reason step-by-step before answering, producing a thinking content block:

  • Adaptive thinking (default for 4.7+ models) — Claude decides how much to think based on task complexity
  • Effort parameter — low, medium, or high controls thinking depth
  • Thinking tokens are billed as output tokens
  • Thinking signatures — Thinking blocks have cryptographic signatures for multi-turn verification
  • Cannot be used simultaneously with temperature > 0

Part 04Delivery, Cost, and Access Paths

What Is Prompt Caching (API)?

Prompt caching lets you reuse repeated prompt prefixes, saving up to 90% on input token costs:

  • Automatic caching — Top-level cache_control on system/tools/messages blocks
  • Explicit caching — Per-block cache_control: {"type": "ephemeral"}
  • 5-minute TTL write = 1.25x base input price; 1-hour TTL write = 2x base price
  • Cache hit = 0.1x base input price (90% discount)
  • Minimum tokens vary by model (1024 for Haiku, 2048 for Sonnet/Opus)
  • Pre-warming: Send a request with max_tokens: 0 to prime the cache without generating output

Part 05Software Engineering Foundations

What Is Version Control?

Version control (Git) tracks changes to code, prompts, and configurations over time. Essential for AI applications because:

  • Track changes — See exactly what changed in a prompt and when
  • Branches — Experiment with prompt variations without affecting production
  • Merge — Combine prompt improvements from multiple contributors
  • Rollback — Revert to a known-good prompt version if quality drops
  • Prompt versioning — Tag prompt releases just like code releases

What Is Code Review?

Peer review of code changes before merging. For AI applications, code review extends beyond traditional code:

  • Review prompts — Are instructions clear? Are examples representative?
  • Review tool definitions — Are schemas correct? Are descriptions accurate?
  • Review eval results — Did the change improve or regress quality?
  • Review not just code — Prompt changes are configuration changes that deserve the same rigor

What Is Refactoring (Small- and Large-Scale)?

Small-Scale Refactoring
  • Rename variables for clarity
  • Extract functions to reduce duplication
  • Simplify conditional logic
  • Improve prompt wording for clarity
Large-Scale Refactoring
  • Restructure prompt architecture
  • Split monolithic agent into hub-spoke
  • Migrate from one model to another
  • Replace inline prompts with versioned files

What Is a REST API?

REST (Representational State Transfer) is the architectural style used by the Claude Messages API:

  • HTTP methods: GET (read), POST (create), PUT (update), DELETE (remove)
  • Stateless — Each request contains all context needed; server stores no session state
  • JSON payloads — Request and response bodies use JSON format
  • The Claude Messages API is a REST API: POST /v1/messages

What Is JSON?

JavaScript Object Notation — the key-value data format used throughout Claude integrations:

  • API requests/responses — All Claude API communication uses JSON
  • Tool schemas — Tool input_schema uses JSON Schema
  • Structured outputs — output_config.format defines JSON response schemas
  • Data types: strings, numbers, booleans, arrays, objects, null

What Is Asynchronous Programming?

Non-blocking execution essential for AI applications:

  • Streaming responses — Process tokens as they arrive without blocking
  • Parallel tool calls — Execute multiple tool calls concurrently
  • Batch processing — Submit batch and poll for results asynchronously
  • Python: async/await with asyncio; client = anthropic.AsyncAnthropic()
  • JavaScript: Promises, async/await; SDK methods return Promises natively

What Are Content Boundaries?

Content boundaries separate user content from instructions to prevent prompt injection:

  • Use XML tags to clearly delimit untrusted content: <user_input>...</user_input>
  • Place instructions in the system prompt, untrusted content in user messages
  • Never concatenate user input directly into instruction strings
  • Use clear delimiters so the model knows what is an instruction vs. what is data

What Is Schema Design?

Designing schemas for tool inputs, structured outputs, and API responses:

  • Use JSON Schema for tool input_schema and output_config.format
  • Keep schemas flat when possible — avoid deeply nested structures
  • Mark required fields explicitly
  • Add descriptions to every property — Claude uses these to understand intent
  • Use enum for fields with finite options to constrain model output

What Is Session Hygiene?

Managing conversation state to keep context clean and effective:

  • When to start fresh — New topic, different task, context window nearing capacity
  • When to summarize — Long conversations where early context is still relevant but verbose
  • Pruning old tool results — Replace large tool outputs with summaries to save tokens
  • Avoiding context pollution — Don't carry irrelevant information from prior turns

What Are Plugin Management and Plugin Dependencies?

  • Managing MCP servers — Configure which external tools are available in settings.json
  • Version compatibility — Ensure MCP server protocol versions match client expectations
  • Graceful degradation — Handle cases where an MCP server is unavailable (fallback to built-in tools or inform user)
  • Tool dependencies — Some tools depend on others (e.g., a deploy tool needs build output)

Designing a Claude Application Across Interfaces

Architecture decisions about where to place different types of instructions:

  • System prompt — Role definition, output format, safety constraints, persistent rules
  • CLAUDE.md — Project architecture, coding standards, build commands, testing patterns
  • Tool descriptions — When to use each tool, what it returns, parameter guidance
  • User prompts — Variable data, per-request questions, context-specific information

Part 10LLM and Technical Fundamentals

What Is a Token?

A token is the fundamental unit of text processing in LLMs. Approximately 4 characters or 0.75 words in English. Tokens are also the billing unit:

  • 1M tokens is approximately 555K words or 750K English words
  • Claude 4.7+ uses an updated tokenizer that produces ~30% more tokens for the same text
  • Everything is counted in tokens: system prompts, messages, tool definitions, images, thinking, and output

What Is a Context Window?

The context window is Claude's working memory — everything it can reference during a single request. It is NOT training data:

  • 1M tokens for Fable, Opus, and Sonnet models
  • 200K tokens for Haiku
  • Everything counts: system prompt, conversation history, tool definitions, images, thinking blocks, and output
  • When the context window fills up, earlier content is either truncated or you must start a new conversation

What Is Sampling (Temperature / Top-p)?

  • Temperature: 0 = deterministic (always picks most likely token), 1 = creative (more randomness)
  • Top-p (nucleus sampling): Considers only tokens whose cumulative probability reaches p. Alternative to temperature.
  • Both control randomness of token selection — do not set both simultaneously
  • Use temperature=0 for classification, extraction, and factual tasks; higher values for creative writing

What Is Nondeterminism in LLMs?

The same prompt can produce different outputs each time. Causes include:

  • Sampling — Random token selection (set temperature=0 for most deterministic)
  • Floating-point math — GPU arithmetic can vary between runs
  • Server-side randomness — Load balancing across different hardware
  • Even with temperature=0, outputs are not guaranteed identical across requests

What Is Next-Token Generation?

LLMs are autoregressive: they predict one token at a time, each conditioned on all previous tokens. Key implications:

  • Order matters — The sequence of previous tokens influences the next prediction
  • Cannot "go back" — Once a token is generated, it becomes context for the next
  • Streaming works because tokens are produced sequentially
  • This is why prompt engineering focuses on setting up the right context before the model generates

  • Zero-shot — No examples, just instructions. Relies on the model's training. Simplest but least reliable.
  • Single-shot (one-shot) — One example demonstrating the desired behavior. Better than zero-shot for format compliance.
  • Multi-shot (few-shot) — 3-5 examples. Recommended for best results. Shows the model the exact pattern to follow.

What Is a WebSocket?

A persistent bidirectional connection between client and server:

  • Used for real-time streaming, chat interfaces, live updates
  • Different from HTTP request/response (HTTP is one-way per request)
  • Claude API uses SSE (Server-Sent Events) for streaming, not WebSocket
  • However, your application may use WebSocket to stream Claude's response to your users

What Are LLMs?

Large Language Models are neural networks trained on vast amounts of text data to understand and generate language:

  • Built on the Transformer architecture with self-attention mechanism
  • Pre-trained on massive text corpora, then fine-tuned for specific behaviors
  • Generate text one token at a time (autoregressive)
  • Claude is Anthropic's family of LLMs, trained with Constitutional AI (CAI) and RLHF

What Are Foundational Models?

Large pre-trained models that serve as a base for many downstream tasks:

  • Examples: Claude (Anthropic), GPT (OpenAI), Gemini (Google), Llama (Meta)
  • Can be used for many tasks without task-specific training
  • Distinguished by scale (billions of parameters) and generality (broad capabilities)
  • Fine-tuning adapts them for specific domains or tasks

Neural Networks: Basics and Types

Neural networks are the computational architecture underlying LLMs:

  • Neurons — Basic processing units that receive input, apply weights, and produce output
  • Layers — Neurons organized in layers: input, hidden (many), output
  • Weights — Learnable parameters adjusted during training
  • Activation functions — Non-linear functions (ReLU, softmax) that enable complex learning

Types of neural networks:

  • Feedforward — Data flows one direction; simplest architecture
  • Recurrent (RNN) — Has loops for sequential data; limited memory
  • Convolutional (CNN) — Specialized for spatial data (images, grids)
  • Transformer — Uses self-attention mechanism; powers all modern LLMs including Claude

Token Counting and Billing

Tokens are the fundamental billing unit. Every element of the API request counts toward the context window:

  • System prompt tokens — Counted as input tokens every request
  • Tool definition tokens — Each tool definition adds tokens to every request
  • Conversation history tokens — Grows with each turn (stateless API resends everything)
  • Image tokens — Calculated from image dimensions: ceil(w/28) * ceil(h/28)
  • Thinking tokens — Billed as output tokens, can be significant with extended thinking
  • Output tokens — The model's generated response text

Use response.usage to track: input_tokens, output_tokens, cache_creation_input_tokens, and cache_read_input_tokens.

Exam Tip Know that tokens are ~4 chars, context window is NOT training data, temperature controls randomness, and LLMs use Transformer architecture with self-attention. Claude API uses SSE for streaming (not WebSocket).

Part 12Cost and Token Management

What Is Token Usage Tracking and Cost Modeling?

Every API response includes a usage field with token counts:

JSON{ "usage": { "input_tokens": 1250, "output_tokens": 480, "cache_creation_input_tokens": 800, "cache_read_input_tokens": 450 } }

Calculate cost: cost = (input_tokens * input_price_per_MTok / 1,000,000) + (output_tokens * output_price_per_MTok / 1,000,000). Track over time for budgeting and anomaly detection.

Prompt Caching in Claude

  • Automatic caching — Set cache_control on top-level blocks (system, tools, messages)
  • Explicit caching — Per-block cache_control: {"type": "ephemeral"}
  • TTL: 5-minute (1.25x write) or 1-hour (2x write); hits cost 0.1x
  • Cache-aware ITPM — Cache reads count at reduced rate toward input token limits
  • Minimum tokens: 1024 (Haiku), 2048 (Sonnet/Opus) to create a cache entry
  • Pre-warming: max_tokens: 0 primes the cache without generating output
  • Invalidation hierarchy: Changing tools invalidates system cache; changing system invalidates message cache. Order: tools → system → messages

Part 13Context Engineering

What Is Tool Output Pruning?

Removing or summarizing old tool results from conversation context to free space. Tool results can be very large (file contents, search results, API responses) and keeping all of them fills the context window quickly.

  • Replace large tool outputs with one-line summaries after the model has processed them
  • Keep only the most recent tool results in full detail
  • Use the model to generate summaries of tool outputs before discarding the originals

What Is Compaction?

Server-side auto-summarization of earlier conversation when tokens approach the context window limit:

  • Preserves key information while reducing token count
  • In Claude Code, triggered via /compact or automatically when context grows large
  • The model summarizes the conversation so far, then continues with the summary as context
  • Trade-off: some nuance may be lost in the summarization

What Is Context Isolation?

Keeping separate agents or conversations in their own context windows:

  • Prevents cross-contamination — Each agent sees only relevant information
  • Each agent has its own context — Worker agents in a hub-spoke model do not see each other's history
  • Reduces context pollution — Irrelevant information from one task does not affect another
  • Enables parallelism — Independent agents can process concurrently

Managing Context to Prevent Drift and Bloat

Strategies for keeping context clean over long conversations:

  • Prune old tool results — Replace verbose outputs with summaries
  • Use compaction — Summarize the conversation when it grows too large
  • Summarize periodically — At natural breakpoints, consolidate what has been accomplished
  • Use memory tool for multi-session persistence instead of keeping everything in context
  • Start fresh for new topics — Begin a new conversation rather than carrying stale context
Exam Tip Tool output pruning replaces large tool results with summaries. Compaction auto-summarizes conversation history. Context isolation keeps agents in separate context windows. These are all strategies to manage the finite context window.

Part 14Prompt Engineering

What Is Prompt Engineering?

Crafting effective prompts to get desired outputs from LLMs. It is an iterative process of writing, testing, and refining instructions. Prompt engineering is as much about testing and measurement as it is about writing.

What Is System vs User Prompt Placement?

System Prompt
  • Persistent instructions, role definition, constraints
  • Invisible to end users
  • Instructions have higher authority
  • Set once, active for entire conversation
User Messages
  • Per-turn input, questions, variable data
  • Contains user's actual request
  • Place untrusted content here, not in system
  • Changes each turn

What Is an Output Constraint?

Rules that limit or shape the model's output:

  • Max length — "Respond in 3 sentences or fewer"
  • Format requirements — "Return valid JSON matching this schema"
  • Language restrictions — "Respond only in Spanish"
  • Style guidelines — "Use a professional, concise tone"
  • Excluded topics — "Do not discuss competitor products"
  • Enforced via system prompt instructions or output_config for structured output

What Is Input Sanitization?

Cleaning and validating user input before sending to Claude to prevent misuse:

  • Prevent prompt injection — Strip or escape characters that could be interpreted as instructions
  • Remove PII — Redact personal information before sending to the API
  • Validate format — Ensure input matches expected structure before processing
  • Escape special characters — Handle XML tags, quotes, and control characters
  • Length limits — Truncate or reject excessively long inputs

Writing and Iterating Effective Prompts

Follow the CERRS framework for effective prompts:

  • Clear — Unambiguous instructions with specific requirements
  • Examples — 3-5 few-shot examples (multi-shot) for best results
  • Role — Define the model's persona and expertise area
  • Reasoning — Ask the model to think step-by-step before answering
  • Structure — Use XML tags, numbered lists, and clear formatting

The Golden Rule: If a human expert would need more context to complete the task, so does the model. Provide all necessary context explicitly.

Placing Instructions Across Components (System vs User)

  • Persistent rules → System prompt (role, format, constraints, safety rules)
  • Variable data → User messages (documents to analyze, questions to answer)
  • Tool guidance → Tool descriptions (when to use, what it returns)
  • Project context → CLAUDE.md (architecture, standards, build commands)
Exam Tip Know the CERRS framework, the difference between system and user prompt placement, and the Golden Rule. Multi-shot (3-5 examples) produces the best results. Use XML tags for structure.

What Is Structured Output?

What Is a Claude Hook?

Shell commands configured in settings.json that execute on specific events. Hooks are deterministic enforcement that prompts cannot override:

  • PreToolUse — Runs before a tool executes (block, modify, or allow)
  • PostToolUse — Runs after a tool executes (validate, log, auto-format)
  • Notification — Runs when Claude sends a notification
  • Stop — Runs when Claude finishes its response
Exam Tip Hooks are code, not prompts — they cannot be overridden by prompt injection. Know the four hook types: PreToolUse, PostToolUse, Notification, Stop. Guardrail layering combines multiple defense layers.

Part 18Tools and Model Context Protocols (MCPs)

Tool Use in Claude

Function calling lets you define tools with JSON Schema that Claude can invoke:

  • Define tools with name, description, and input_schema (JSON Schema)
  • Claude calls them — Returns tool_use blocks with tool name and arguments
  • You execute and return tool_result blocks
  • Client-side tools — Executed by your code (API calls, database queries, file operations)
  • Server-side tools — Executed by the model itself (web search, code execution in Managed Agents)

How to Write a Complete Tool Description

A well-written tool description tells the model four things:

  1. What it does — "Searches the product catalog by keyword"
  2. When to use it — "Use when the user asks about product availability or pricing"
  3. What it returns — "Returns a JSON array of matching products with name, price, and stock"
  4. How it differs from similar tools — "Unlike search_docs, this searches only the product database, not documentation"

Add descriptions to every parameter with types and examples.

What Is a Programmatic Gate?

A code-level check that blocks or modifies tool calls — not a prompt, but actual program logic:

  • More reliable than prompt-based restrictions (cannot be overridden by clever prompting)
  • Check tool name and arguments before execution
  • Enforce business rules (e.g., cannot delete more than 10 records at once)
  • Implemented via hooks or application-level middleware

What Is an Approval Pattern?

Requiring human confirmation before executing certain tool calls:

  • Especially important for destructive or irreversible actions (delete, deploy, send email)
  • Implement via hooks (PreToolUse returns "needs_approval") or application-level UI
  • Claude Code's default mode requires user approval for most tool calls unless auto mode is enabled
  • In CI/CD, use --allowedTools to whitelist safe tools and block everything else

What Is a Claude Skill?

A packaged, repeatable workflow invoked by name:

  • Examples: /review-pr, /deploy, /test, /security-review
  • Progressive disclosure: loads instructions on demand rather than always occupying context
  • Can include code, scripts, and multi-step logic
  • Built-in skills (e.g., /review) and custom skills (defined by the project)

What Is a Model Context Protocol (MCP) Server?

A standardized server that exposes tools, resources, and prompts to AI clients:

  • Connects via SSE or WebSocket for real-time communication
  • Supports OAuth for authentication
  • Enables tool discovery — clients can query what tools a server offers
  • Standardized protocol means any MCP-compatible client can use any MCP server

Agent Communication Protocol (ACP)

A protocol for agents to communicate with each other:

  • Standardized message format for inter-agent communication
  • Discovery — Agents can find and identify other agents
  • Capability negotiation — Agents declare what they can do
  • An emerging standard for multi-agent systems, complementary to MCP

Agent-to-Agent (A2A)

Google's protocol for direct communication between agents without a central coordinator:

  • Peer-to-peer collaboration — Agents communicate directly
  • Shared state — Agents can share working context
  • Distributed problem solving — Tasks split across agents without a hub
  • Different from hub-spoke: no single orchestrator, agents are peers

What Are MCP Resources, Tools, and Prompts?

MCP servers expose three primitives:

  • Resources — Data sources the agent can read (files, databases, APIs). Read-only context.
  • Tools — Functions the agent can call (create, update, delete, search). Executable actions.
  • Prompts — Pre-built prompt templates the server provides. Reusable instruction sets.
Exam Tip Know the three MCP primitives (Resources, Tools, Prompts). Understand ACP (agent-to-agent standardized communication) vs A2A (Google's peer-to-peer protocol). Programmatic gates are code, not prompts.
