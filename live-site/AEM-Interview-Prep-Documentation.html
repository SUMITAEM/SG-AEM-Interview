Authentication System

The site is fully gated behind Firebase Authentication. Users must sign in before accessing any content.

Supported Login Methods

  • Google Sign-In — One-click login via Google popup (falls back to redirect on mobile/popup blockers)
  • Email/Password — Traditional sign-up and sign-in with email and a password (min 6 chars)

How It Works

1
User visits the site — A full-screen login overlay blocks all content.
2
User signs in — Via Google or email/password.
3
Firebase verifies — Auth state listener detects the signed-in user.
4
Content unlocks — Overlay fades out, app becomes visible, user profile shows in sidebar (desktop) or floating avatar (mobile).
5
User data saved — Name, email, login count, and timestamp stored in Firestore. Analytics login event fires.

Important: Auth vs Firestore Users

Firebase Auth and Firestore are separate systems. If user counts don't match, it means Firestore writes failed (usually expired security rules). Use the admin panel (?admin=sg2024) to diagnose. See the Admin Panel section below.

Firestore Security Rules

The following permanent rules (no expiration) must be applied. These replaced the original 30-day test-mode rules that caused new users to stop appearing in Firestore after September 2026.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      allow read, write: if request.auth != null
                         && request.auth.uid == userId;
    }
  }
}

Apply at: Firestore → Rules

Lesson Learned: Expired Rules Incident (Sep 2026)

Firebase's default test-mode rules expired after 30 days, silently blocking all Firestore writes. Users could authenticate (Auth) but their data wasn't saved (Firestore). The fix was applying permanent rules (above) and adding error logging to the saveUserData() function so failures are no longer silent.

Single-Device Enforcement (Anti-Sharing)

Prevents users from sharing their login credentials. Only one active session is allowed per account at a time.

How It Works

1
User signs in — A unique session ID is generated and stored in Firestore (activeSessionId).
2
Monitoring starts — Every 30 seconds, the app checks if its local session ID still matches Firestore.
3
Another device signs in — The new device overwrites activeSessionId with its own session ID.
4
Old device detects mismatch — Shows a "Session Active Elsewhere" overlay. User can either reclaim the session or sign out.

Firestore Fields Added

FieldTypeDescription
activeSessionIdstringUnique ID of the currently active session
activeDevicestringUser-Agent of the active device (first 120 chars)
sessionStartedtimestampWhen the current session was started
