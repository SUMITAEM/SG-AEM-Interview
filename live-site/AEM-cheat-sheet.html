01 AEM Architecture & Stack

▶

Technology Stack

AEM Application +-- Apache Sling (RESTful resource resolution) | +-- JCR / Apache Jackrabbit Oak (content repository) | +-- OSGi / Apache Felix (modular runtime) | +-- Java VM
  • AEM = CMS built on Apache Sling + JCR (Jackrabbit Oak) + OSGi (Apache Felix)
  • Everything is a JCR node (tree of nodes and properties)
  • Sling maps URLs to JCR resources; OSGi manages service lifecycle

Instances

InstancePurposePort
AuthorContent creation, editing, workflows, preview4502
PublishContent delivery to end users4503
DispatcherApache module: caching + load balancing + security80/443

Replication

  • Forward: Author → Publish (activate/publish content)
  • Reverse: Publish → Author (e.g., user-generated content)
  • Agents configured at /etc/replication/agents.author

Content Hierarchy

PathPurpose
/contentSite pages and DAM assets
/appsProject code: components, templates, servlets
/libsAEM product code (never modify)
/confEditable templates, policies, cloud configs
/etcLegacy configs, designs, workflow models
/varAudit logs, workflow instances, temp data
/homeUsers and groups
/oak:indexOak index definitions

Run Modes

  • Set via sling.run.modes in start script or JVM args
  • Types: author, publish, dev, stage, prod
  • Control which OSGi configs activate per environment

Key Recall

  • AEM = Sling + JCR (Oak) + OSGi (Felix) + Java
  • Author (4502) creates; Publish (4503) delivers; Dispatcher caches
  • /apps overlays /libs — never modify /libs directly
  • Run modes control OSGi config activation per environment

02 AEM Project Structure & Archetype

▶

Maven Archetype

  • Generates multi-module project: mvn archetype:generate -DarchetypeGroupId=com.adobe.aem -DarchetypeArtifactId=aem-project-archetype
  • Current version: Archetype 47+ for AEMaaCS

Module Structure

ModulePurpose
core/Java OSGi bundle: servlets, services, Sling Models, workflows
ui.apps/AEM components (HTL, dialogs, clientlibs) — immutable in cloud
ui.content/Sample content and templates — mutable
ui.config/OSGi configurations per runmode
ui.frontend/Webpack build for clientlibs (TS/SCSS)
all/Aggregation package for deployment
dispatcher/Dispatcher configs (Apache + dispatcher module)

Build Commands

# Full build + deploy to local author
mvn clean install -PautoInstallSinglePackage

# Core bundle only (faster)
mvn clean install -pl core -PautoInstallBundle

# Frontend only
cd ui.frontend && npm run build

# Build without tests
mvn clean install -DskipTests

POM Hierarchy

  • Reactor parent POM at project root
  • Each module has its own POM inheriting from parent
  • uber-jar dependency for AEM 6.5; aem-sdk-api for AEMaaCS

Key Recall

  • core = Java, ui.apps = components, ui.config = OSGi configs, ui.frontend = Webpack
  • -PautoInstallSinglePackage deploys everything; -PautoInstallBundle deploys core only
  • all/ aggregates everything into a single deployable package

03 OSGi Framework & Services

▶

Core Concepts

  • OSGi = modular Java; hot-deploy/update/remove bundles without restart
  • Bundle = JAR with OSGi metadata in MANIFEST.MF
  • Component = class managed by OSGi with lifecycle + DI
  • Service = interface registered in the OSGi service registry

Bundle Lifecycle

INSTALLED --> RESOLVED --> STARTING --> ACTIVE | UNINSTALLED <-- STOPPING <-----------+
  • INSTALLED: deployed but dependencies unresolved
  • RESOLVED: all imports satisfied; ready to start
  • ACTIVE: running, services registered
  • Stuck in INSTALLED = missing package import

DS R6 Annotations

AnnotationPurpose
@ComponentDeclares DS component (auto-registers as service if implements interface)
@ReferenceInject another OSGi service
@ActivateCalled when component activates
@DeactivateCalled when component deactivates
@ModifiedCalled when configuration changes at runtime
@Designate(ocd=...)Links component to its config interface

OSGi Configurations

  • Config interface: @ObjectClassDefinition + @AttributeDefinition
  • File naming: com.example.MyService.cfg.json (preferred), .config, .xml
  • Run mode folders: config.author, config.publish, config.dev, config.stage
  • Factory configs: append ~instance-id to PID

Felix Console

URLPurpose
/system/console/bundlesView all bundles and their state
/system/console/componentsView DS components
/system/console/configMgrManage OSGi configs
/system/console/servicesView registered services
/system/console/depfinderFind package dependencies

Service Ranking & Factories

  • Multiple impls: highest ranking wins — @Component(property="service.ranking:Integer=1000")
  • Default ranking = 0; use to override OOTB implementations
  • Service factories: multiple instances of the same service (factory configs)

Key Recall

  • Bundle stuck in INSTALLED = missing package import (check depfinder)
  • DS R6 (@Component, @Reference) preferred over SCR/R4
  • Config naming: PID + run-mode folder determines activation
  • Higher service.ranking = higher priority

04 Apache Sling & Resource Resolution

▶

What is Sling?

  • RESTful framework mapping HTTP URLs to JCR resources
  • Request flow: URL → Resource → Script/Servlet
  • Content-centric: URL determines the node, sling:resourceType determines the rendering

URL Decomposition

/content/mysite/en/page.selector1.selector2.html/suffix?key=val |__________________________| |_________________| |__| |_____| |______| resource path selectors ext suffix query

Servlet Registration

By Path

  • sling.servlet.paths=/bin/myservlet
  • Ignores resource type
  • Cannot be ACL-controlled via JCR
  • Simpler; utility endpoints

By Resource Type (Preferred)

  • sling.servlet.resourceTypes=myapp/page
  • Tied to resourceType + selectors + extension
  • Respects JCR ACLs
  • Recommended approach
  • SlingAllMethodsServlet = GET, POST, PUT, DELETE
  • SlingSafeMethodsServlet = GET and HEAD only

ResourceResolver

  • Session-based — MUST close if opened manually (try-with-resources)
  • Never use getAdministrativeResourceResolver() (deprecated)
  • Use service users: map via Sling Service User Mapping OSGi config
  • Get resolver: resolverFactory.getServiceResourceResolver(authInfo)

Sling Resource Merger

  • /apps overlays /libs — customization without modifying /libs
  • Properties: sling:hideResource, sling:hideChildren, sling:orderBefore

Key Recall

  • Sling = URL → Resource → Script/Servlet (content-centric)
  • Servlet by resourceType is preferred over path-based
  • ALWAYS close manually-opened ResourceResolvers
  • Use service users, never admin resolvers

05 Sling Models

▶

Basics

  • @Model(adaptables={Resource.class, SlingHttpServletRequest.class})
  • Injection strategy: defaultInjectionStrategy = OPTIONAL or REQUIRED
  • Interface + Impl pattern recommended

Injection Annotations

AnnotationInjects
@ValueMapValueJCR property from resource's ValueMap
@ChildResourceChild node as a Resource
@SelfThe adaptable itself (request/resource)
@OSGiServiceAn OSGi service reference
@ResourcePathResource at a given JCR path
@ScriptVariableScript binding (currentPage, designer, etc.)
@SlingObjectSling objects (ResourceResolver, Resource, etc.)

Lifecycle & Export

  • @PostConstruct: init logic after all injection completes
  • @Exporter(name="jackson", extensions="json"): JSON export via .model.json extension

Code Example

@Model(adaptables = Resource.class,
       defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL)
public class HeroModel {

    @ValueMapValue
    private String title;

    @ValueMapValue(name = "fileReference")
    private String imagePath;

    @PostConstruct
    protected void init() {
        if (title == null) title = "Default Title";
    }

    public String getTitle() { return title; }
    public String getImagePath() { return imagePath; }
}

Testing

  • AEM Mocks (io.wcm): AemContext provides mock JCR, ResourceResolver, Sling
  • Mockito for external service dependencies
  • Never make real HTTP calls in tests

Key Recall

  • @ValueMapValue is the most common injection annotation
  • Use OPTIONAL strategy to avoid NPEs on missing properties
  • @PostConstruct runs after injection — good for validation/defaults
  • @Exporter enables JSON export via .model.json extension

Global Objects

Template + Call Pattern

<!-- Define template -->
<sly data-sly-template.card="${@ title, desc}">
  <div class="card">
    <h3>${title}</h3>
    <p>${desc}</p>
  </div>

<sly data-sly-call="${card @ title='Hello', desc='World'}" />

  • Default context is 'html' — auto-escaped for XSS
  • data-sly-resource includes components; data-sly-include includes HTL files
  • Never use context='unsafe' unless absolutely necessary

08 Editable Templates & Policies

▶

Editable Templates (Recommended)

  • Location: /conf/mysite/settings/wcm/templates
  • Template Types define the blueprint → Templates define page structure
  • Three layers:
    • Structure: locked components (header/footer)
    • Initial content: default content for new pages
    • Policies: component + style system configuration
  • Template editor: /editor.html/conf/...

Static Templates (Legacy)

  • Location: /apps/mysite/templates
  • No runtime editing — changes require code deployment

Content Policies

  • Location: /conf/mysite/settings/wcm/policies
  • Control: allowed components, style system classes, design properties
  • Applied via policy mapping in template editor

Style System

  • Add CSS classes to components without code changes
  • Configure in template policies → component → style tab
  • Groups: e.g., "Layout" (full-width, centered), "Color" (dark, light)

Layout Container

  • Responsive grid with configurable breakpoints
  • Authors can resize components in the grid
  • Allowed components controlled per template via policies

Key Recall

  • Editable (/conf) = recommended; Static (/apps) = legacy
  • Template = structure (locked) + initial (defaults) + policies (config)
  • Style System adds CSS classes without code — configured in policies
  • Layout container = responsive grid; breakpoints configurable

09 Workflows & Launchers

▶

Workflow Engine

ConceptDetails
EngineGranite workflow engine (models at /var/workflow/models)
Step typesProcess, Participant, OR Split, AND Split, Container
OOTB examplesRequest for Activation, DAM Update Asset
PayloadPath to the content node being processed

Custom Process Step

@Component(service = WorkflowProcess.class, property = {
    "process.label=My Custom Step"
})
public class MyStep implements WorkflowProcess {
    private static final Logger LOG =
        LoggerFactory.getLogger(MyStep.class);

    @Override
    public void execute(WorkItem workItem,
                        WorkflowSession session,
                        MetaDataMap args)
                        throws WorkflowException {
        String path = workItem.getWorkflowData()
            .getPayload().toString();
        LOG.info("Processing: {}", path);
    }
}

Workflow Launchers

  • Auto-trigger on node created/modified/deleted
  • Conditions: nodeType, glob (path pattern), eventType
  • Configured at /libs/settings/workflow/launcher (overlay in /conf)

Transient Workflows

  • Don't persist full history — better performance
  • Used for DAM asset processing
  • Required in AEMaaCS (no persistent workflow history)

Key Recall

  • Custom step: implement WorkflowProcess.execute()
  • Launchers auto-trigger workflows on JCR events
  • Transient workflows = no history persistence = better performance
  • AEMaaCS requires transient workflows

13 JCR Queries & Oak Indexes

▶

Query Languages

1. SQL2 (Preferred)

SELECT * FROM [cq:Page] AS p
WHERE ISDESCENDANTNODE(p, '/content/mysite')
AND p.[jcr:content/jcr:title] = 'Home'

2. XPath (Legacy)

/jcr:root/content/mysite//element(*, cq:Page)
  [jcr:content/@jcr:title = 'Home']

3. QueryBuilder (AEM-Specific)

path=/content/mysite
type=cq:Page
property=jcr:content/jcr:title
property.value=Home
orderby=@jcr:content/jcr:created
orderby.sort=desc
p.limit=10
  • REST: /bin/querybuilder.json?path=/content&type=cq:Page
  • Predicates: fulltext, daterange, tagid, nodename, hasPermission

Oak Index Types

TypeUse CaseNotes
LuceneFull-text search, sortingMost versatile
PropertyEquality lookupsFast for exact matches
OrderedRange queriesDeprecated in favor of Lucene
  • Defined at /oak:index with oak:QueryIndexDefinition node type
  • NEVER rely on traversal queries in production
  • Debug: /system/console/queryperformance, explain query

Common Node Types

Node TypeUsage
nt:unstructuredFlexible, no schema (most common)
cq:PageAEM page
cq:PageContentPage jcr:content child
dam:AssetDAM asset
sling:FolderFolder with resourceType

Key Recall

  • SQL2 = preferred; QueryBuilder = predicate-based REST API
  • ALWAYS create Oak indexes — traversal = performance disaster
  • nt:unstructured = most common; cq:Page = page nodes
  • Debug queries at /system/console/queryperformance

14 Dispatcher & Caching

▶

What is Dispatcher?

  • Apache module: caching + load balancing + security filtering
  • Sits in front of AEM Publish instance

Request Flow

Browser --> CDN --> Dispatcher (Apache) --> AEM Publish ^ | | Cache Layer | (static HTML files) +--- cached response

Configuration (dispatcher.any)

SectionPurpose
/filterAllow/deny URL patterns (whitelist approach)
/cacheWhat to cache: rules, docroot, statfileslevel
/invalidateAuto-invalidation rules on publish
/rendersAEM Publish instances (render farm)
/virtualhostsDomain/hostname matching

Cache Invalidation

MethodHow
Auto-invalidationOn publish, .stat file touched; stale cache re-fetched
statfileslevelHigher = more targeted invalidation
TTL-basedmax-age headers; cache expires after time
Flush agentsReplication agents trigger dispatcher flush

Security Filters

  • Block: /crx, /system/console, /bin/querybuilder.json
  • Filter selectors to prevent DoS via selector bombing
  • Vanity URLs: short URLs mapped to content paths
  • CDN (Fastly, CloudFront, Akamai) sits in front of Dispatcher

Key Recall

  • Dispatcher = caching + load balancing + security
  • statfileslevel controls invalidation granularity
  • Caching: Browser → CDN → Dispatcher → AEM Publish
  • Always block sensitive paths in /filter rules

15 ClientLibs & Frontend

▶

ClientLibs Basics

  • Node type: cq:ClientLibraryFolder
  • categories: unique ID (e.g., mysite.page)
  • dependencies: other clientlibs loaded before
  • embed: merge into single file (better performance)
  • css.txt / js.txt: file lists defining load order

Including in HTL

<sly data-sly-use.clientlib=
  "/libs/granite/sightly/templates/clientlib.html">
  <sly data-sly-call=
    "${clientlib.all @ categories='mysite.page'}"/>
</sly>
<!-- .css = CSS only, .js = JS only, .all = both -->

Webpack / Frontend Build

  • ui.frontend: Webpack + TypeScript + SCSS
  • Output compiled into /apps/mysite/clientlibs
  • npm build → Maven copies to ui.apps → deployed

Featureembeddependencies

  • Versioned URLs: /etc.clientlibs with long cache TTL
  • Minification: built-in AEM minification or Webpack

20 Performance & Optimization

▶

Caching Layers

Browser Cache --> CDN --> Dispatcher Cache --> AEM Publish (max-age) (TTL/rules) (stat file) (renders)
  • Set appropriate Cache-Control headers
  • Use stale-while-revalidate for better UX
  • Cache static resources aggressively; invalidate on publish

Query Performance

DoDon't
Create custom Oak indexesRely on traversal queries
Restrict with ISDESCENDANTNODEQuery from root (/)
Use p.limit to cap resultsFetch unbounded result sets
Monitor /system/console/queryperformanceDeploy without testing

Code Best Practices

  • ResourceResolver: always close in try-with-resources; use service users
  • HTTP clients: set timeouts (connect + socket); close in try-with-resources
  • Sling Models: prefer OPTIONAL strategy; use @PostConstruct wisely
  • Logging: SLF4J only; never System.out; never log PII

Frontend Performance

  • Lazy load images and below-the-fold components
  • async / defer on script tags
  • Embed clientlibs to reduce HTTP requests
  • Core Web Vitals: LCP, FID/INP, CLS

Monitoring

ToolPurpose
request.logRequest timing + response codes
error.logErrors and exceptions
/system/console/queryperformanceSlow/popular queries
/system/healthAEM Health Check dashboard

Key Recall

  • Cache: Browser → CDN → Dispatcher → AEM
  • ALWAYS create Oak indexes; traversal = unacceptable in production
  • Close ResourceResolvers; leaks = memory exhaustion
  • Monitor: request.log, error.log, query performance console

  • Blue-green deployments for zero downtime

Key Recall

  • Pipeline: build → code quality → security → deploy
  • Full-stack, front-end, and config pipeline types

22 Context-Aware Configuration

▶

What is CAConfig?

  • Configuration that varies by content path
  • Buckets stored at /conf/mysite/sling:configs
  • @ContextAwareConfiguration annotation on config interface

Inheritance

  • Cascades from /conf/global → site-level → page-level
  • More specific config overrides global
  • Access: resource.adaptTo(ConfigurationBuilder.class)

Use Cases

  • Social media config per site
  • Analytics tracking IDs per region
  • API endpoints per environment/site
  • Feature flags per content tree

Code Example

@ContextAwareConfiguration
public @interface SocialConfig {
    @Property(label = "Facebook App ID")
    String facebookAppId() default "";

    @Property(label = "Twitter Handle")
    String twitterHandle() default "";
}

// Usage in Sling Model:
ConfigurationBuilder cfgBuilder =
    resource.adaptTo(ConfigurationBuilder.class);
SocialConfig config =
    cfgBuilder.as(SocialConfig.class);

Key Recall

  • CAConfig = configuration that varies by content path
  • Inheritance: /conf/global → site → page (most specific wins)
  • Access via resource.adaptTo(ConfigurationBuilder.class)

23 Schedulers, Events & Jobs

▶

OSGi Scheduler

  • @Component with scheduler.expression (cron syntax)
  • Or use Scheduler service API: scheduler.schedule()
  • Runs on all cluster nodes unless configured otherwise

Sling Jobs (Preferred for Reliability)

  • Guaranteed execution with retry
  • Clustering-safe — executed on exactly one node
  • JobManager.addJob(topic, properties)
  • JobConsumer: process jobs by topic

Event Handling

MechanismUse Case
OSGi EventHandlerReact to OSGi events (fire-and-forget)
JCR ObservationObservationManager, EventListener on node changes
ResourceChangeListenerModern Sling approach for resource changes
Sling JobsGuaranteed processing with retry

Scheduler Code Example

@Component(service = Runnable.class, property = {
    "scheduler.expression=0 0/5 * * * ?",
    "scheduler.concurrent=false"
})
public class MyScheduler implements Runnable {
    @Override
    public void run() {
        // runs every 5 minutes
    }
}

Key Recall

  • Sling Jobs = guaranteed execution + retry + cluster-safe
  • Scheduler = cron-based; runs on all nodes by default
  • ResourceChangeListener = modern Sling approach for observing changes

RequestConfig config = RequestConfig.custom()

    .build();

        HttpClients.custom()
            .setDefaultRequestConfig(config)
            .build()) {
    HttpGet get = new HttpGet(url);

    }
}
